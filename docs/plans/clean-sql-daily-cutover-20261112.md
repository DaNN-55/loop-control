## 目标与现状

将现有原生 PostgreSQL 17 日常库从 `legacy-v1` 转为 `clean-v2`，采用本次已验证的 166–170 退役迁移；保留账号、规则版本、任务、候选、音轨、费用、历史记录及媒体引用的身份和原值。原生数据库迁移已经完成，本次不更换数据库产品、集群、主版本或媒体盘。

当前部署固定连接 `127.0.0.1:54330/loop_control`，应用与 Worker 分别使用 `loop_app`、`loop_worker`；原生集群数据目录、socket、system identifier 受身份校验。日常 ledger 当前为 162 条、最后为 165；没有采用 clean-v2 或 166–170。旧 Docker 日常库仍作为更早的冻结回退材料保留，不直接用它覆盖更新后的原生库。

默认 `runtime:migrate` 不跨代；`schemaMigrationPlan(..., true)` 才会计划 clean-v2 转换和当前前向迁移。现有 `restoreNativeBackup` 只允许特定新目标，并复制到新的媒体目录，还排除本地登录凭据/会话；它不是本次“只换数据库、保留原媒体位置”的采用命令。不得改日常配置去绕过这些边界。

## 推荐方式

在同一个原生 PG17 集群创建独立候选库，例如 `loop_control_candidate_<id>`。保持日常应用继续使用原库完成预演；最终停写后，以最终完整快照重新建立候选库，显式转换并对账。通过后，从 `postgres` 维护连接交换数据库名称，让新的库继续叫 `loop_control`，旧库改名冻结保留。

这样无需修改固定的数据库名、端口、集群目录、四个业务角色、Keychain 引用或媒体路径。数据库 OID 会改变，所有新旧库身份、数据库级设置和交换阶段必须记录。改名要求不连接正在改名的数据库，并清空两个目标库的客户端连接；参见 [PostgreSQL 17 ALTER DATABASE](https://www.postgresql.org/docs/17/sql-alterdatabase.html)。不把两个改名步骤假定为天然无中断的操作：任何中断都依据持久日志与 OID 判断当前阶段，再恢复或回退，禁止盲目重放。

## 切换前必须补齐的准备

1. 编写一次性、受范围限制的采用控制器和只读预检：固定项目、原生集群、源库/候选库名称、目录身份、代码提交和 SQL manifest；包含阶段日志、已验证对象 OID、重复执行拒绝及恢复入口。当前尚无这个控制器，本轮不实现或运行。
2. 在专属 VM 验证正常交换、改名中断、旧库回退和幂等拒绝；在独立 Mac 原生临时集群验证工具/连接/改名流程。既有 schema 验收不能替代库名交换演练，不使用日常媒体和秘密做试验。
3. 验证“待上线运行包 + 原代际库”和“待上线运行包 + 新代际库”两套组合，确保简单回退确实可启动。若新版不兼容旧库，先准备并演练旧运行包的安全启动方式；不能在切换窗口里试验，也不能用 `git reset` 覆盖并行工作。普通启动会检查源码与准备产物，不能只改一个运行指针就假定能回退。
4. 确认当前媒体根、账号目录、实际使用的 OpenChatCut SQLite/工程、Keychain、恢复回执、部署文件及所有运行消费者的范围。演练与正式采用均不移动或重绑媒体，不替换 SQLite，不重置 Owner 或数据库密码。

上述准备及日常停启/切换需未来明确授权。本轮提交代码不等于授权执行。

## 正式执行步骤

### 1. 锁定版本与只读预检

- 固定本地 main 的目标提交及准备包摘要；确认没有新并行改动混入运行包。保存当前实际运行版本，而不只记录最新 main。
- 重新核对集群标识、工具版本、端口、源库 OID、ledger 和 manifest；检查磁盘空间、数据库体积及恢复包落点，不承诺固定停机分钟数。
- 检查 ready/running 任务、供应商 started/received/unknown、费用预留、活动租约、发布 hold、目录迁移、清理/恢复作业和 Studio 会话。出现待结果或待发布内容，先处理原操作，不取消任务、不自动重发以制造空闲状态。
- 候选库仅供管理员诊断，不接生产 Worker、自动化消费者或真实供应商。预演使用隔离媒体副本；生产候选仅验证原媒体引用，不打开或写入真实工程。

### 2. 保存退出并停写

- Owner 保存并退出 Studio；停止本项目 App、Worker、原生自动化等实际消费者，保留 PG 集群运行。
- 清点源库和候选库连接为零（维护连接在 `postgres`）；发现不明连接即停止推进，不批量终止其他数据库、预览或项目的进程。
- 保存停写时间与任务/回执最终状态；此后不得让旧应用自动重连或出现双写。

### 3. 制作最终恢复材料

- 做一次性完整逻辑导出，包含业务表、技术 ledger、Owner 本地登录凭据摘要、会话等控制记录，以及 Owner/ACL、数据库级参数和数据库-角色设置。材料仅存本机私有目录，权限 0700/0600，不进 Git，不打印凭据内容。
- 同集群的四个业务角色、密码和 Keychain 不重置；单独记录角色属性/成员/授权，防止候选恢复改变集群权限。
- 保存部署文件、原恢复回执和实际运行包；对媒体目录及全部实际工程做一致性清单，必要的文件/SQLite恢复副本在消费者退出后制作。不要把运行中的 SQLite 主文件单独复制当作一致性备份。
- 现有常规业务备份包排除了凭据与会话，不能作为唯一的无损回退资料。本次专用材料验证可恢复后，才继续；不因此启用周期自动备份。

### 4. 从最终快照重建候选并显式迁移

- 使用全新、唯一候选名称，拒绝覆盖任何现存源库/候选库。候选继承源库编码、locale、扩展、Owner 与 ACL，恢复全库数据及必要的数据库级设置。
- 恢复操作明确指定候选目标，不使用会创建/连接现用 `loop_control` 的恢复选项；不执行现有工具的媒体复制、挂载重绑或 Owner 初始化步骤。
- 先验证原代际数据与 ledger 完整，再在候选中通过共享 catalog 显式执行 clean-v2 转换及 166–170。保留原 162 条 ledger，不伪造旧迁移；按当前固定目录，目标预计为 168 条，实际由锁定 catalog 计算并验证。
- 不采用未经演练的增量同步。预演完成后若日常发生过新写入，使用停写后的最终完整快照重建候选，避免遗漏控制记录和中间状态。

### 5. 对账与采用门槛

必须核对全部业务/控制行、稳定 ID、时间精度、主外键、序列、枚举、函数、触发器、RLS、ACL、角色、数据库级设置及 ledger。只允许已批准的两个历史规划表改名、只读权限收紧、旧入口拒绝和辅助对象退役等差异；不能仅比较行数。

同时验证原媒体与音频字节/引用、目录身份、实际 SQLite 工程 ID/版本、原生保存/重开边界、Owner 凭据摘要及 Keychain 引用不变。原任务未知状态和发布保护必须保持，不重生成、不自动采用、不重新计费。

候选阶段使用专门的只读检查，生产消费者仍关闭。基于真实对账生成数据库采用回执并保留旧回执；其数据库名最终必须匹配 `loop_control`，媒体与发布保护符合现有启动校验。禁止手改 `passed:true` 或复用不匹配的历史回执来绕过校验。

### 6. 名称交换与冻结旧库

- 在 `postgres` 维护连接记录源/目标 OID及现名，再次确认无目标连接。
- 将原 `loop_control` 改名为唯一的 `loop_control_legacy_<id>`，将候选改名为 `loop_control`；冻结旧库新连接，保留其数据、原参数及授权快照。不 DROP 旧库。
- 按真实阶段原子发布已验证的采用回执；检查固定数据库名、集群/端口、媒体根、账号目录、OpenChatCut 和 Keychain 绑定符合部署约束。部署文件如确实需要调整回执引用，仅改已审查字段，并保留原文件。
- 改名或回执发布中断时，保持 App/Worker 关闭，按 OID 与阶段日志恢复，不启动任意“看起来叫 loop_control”的库。

### 7. 启动与验收

- 改名后先在消费者关闭状态完成只读连接、权限、schema、ledger、文件引用和采用回执检查。
- 只有通过后才启动单套 App/Worker/自动化，检查登录、账号/系列、生产单、历史、当前制作选择、字幕、工程、系统状态及资源限额。维持全局并发 2、本机重任务 1，自动备份关闭。
- **从启动 App 或任何消费者起即按“可能已发生新写入”处理**。登录、健康任务和控制记录也可能写库，不能等到第一次视频生产才算进入写入阶段。阶段前后留完整对账检查点，切换验收不自动提交付费生成。

## 回退安排

| 时点 | 处理 | 数据边界 |
| --- | --- | --- |
| 最终导出/候选迁移/对账失败，尚未交换 | 保留失败候选和日志，恢复源库允许连接，按已验证运行组合恢复原服务 | 源库未迁移，媒体/SQLite未改，不丢原业务 |
| 改名/回执发布中断，尚未启动消费者 | 保持停写，按OID/阶段日志还原源库名称和连接设置，恢复原回执及对应运行组合 | 不假定改名原子，也不覆盖任一目标 |
| 交换成功，消费者仍未启动，仅做过只读验证 | 将新库改名隔离，将冻结旧库恢复为loop_control，恢复原连接设置/回执和已验证运行组合 | 可按切换前检查点回退；新库保留，不直接删除 |
| App/Worker/自动化已启动，或已有任何新写入 | 立即停写并保留新库完整快照、控制/请求/费用/发布状态及媒体/SQLite的一致性材料；优先在新代际恢复副本修复并验证 | **不能只换回旧库**，否则丢失切换后的记录；现有代码没有经过验证的跨代增量回灌工具 |

写入后若确需退回旧 schema，先在隔离副本实施反向映射和逐项无损对账，批准所有无法还原的取舍后再操作；做不到时保持维护窗口或恢复到修复后的新代际。不得默默舍弃新数据，也不能把“保留了旧库”等同于已有无损一键回退。

## 旧库与材料保留

建议至少保留到新库完成一次真实制作、一次验证恢复且观察无异常之后，再单独讨论清理；不设自动删除日期。原 Docker 回退库、其他字幕预览、日志、缓存和其他暂缓项不在本次切换清理范围。

切换完成的交付应包含：实际提交/运行包、源/目标身份、每阶段日志、逐项对账、采用回执、主流程检查和回退演练收据。方案或隔离 SQL 通过均不能替代这份日常执行证据。
