# 当前制作、旧流程和命名全面替换方案：197 副本评估

日期：2026-11-14。状态：Proposed，仅测试后方案，不执行改造。依据[本轮新生产单与埋点报告](../verification/production-replacement-assessment-197-20261114/REPORT.md)、本轮有效 SQL／依赖及固定源码；保持 ADR-0066／0068／0069 的既有架构方向，不另建一套制作系统。

## 结论

**建议保留现有内核，做有边界的局部重构和迁移，不整体重写。**本轮新单已不依赖旧审核包、镜头草稿或审批，真实保存、重开、导出、交付和相关埋点均可完成。应继续使用已验证的 Owner 事务、执行快照、原生工程、文件身份、候选确认、费用及 Worker 保护。

剩余问题主要是三件事：一部分旧作品还不能完整接入；后端仍保留第二套旧操作和隐式 SQL 动作；共享实现的名称、类型与职责不一致。另外，正式 MP4 的棋盘格是独立输出缺陷，和 SQL 清理、改名字没有关系。

“完全清理”的可检查目标是：当前用户操作与当前执行只有一套制作模型，当前代码不再依赖退役入口；旧内容经版本化适配器读取、接入和恢复。**原数据、冻结快照、草稿、音轨、审批、原包、已应用迁移和备份原名保留。**全文没有旧字符串，既不是必要条件，也不是安全目标。

## 哪些已经完成，不需要重新做

- 原八类第 1 类旧生成脚本链已退役；独立旧建单 RPC 已有 186 迁移，不再安排一次删除。
- 当前独立制作基准、稳定镜头、v3 图片输入和默认准备链已存在。本轮新单旧审核包／镜头草稿／审批均为 0，不能再把它们描述成当前制作的必经结构。
- 共用文件时交付音轨身份错误已不再复现；本轮两条轨和采用正文均正确。历史主脚本关联也已有受控补齐实现；本轮没有重新跑全部恢复，不以源代码存在代替最终恢复矩阵。
- 制作里程碑、声音使用和本机导出观察已经有实现且本轮联测通过，不再列成待开发。
- v2 保存计划只读与显式导入、无原生成品的已确认绑定接入、未确认选择导入已有当前实现和正反测试；后续补的是完整覆盖、产品入口和退出条件。

## 先处理的真实缺口

| 优先级与部分 | 大白话：问题在哪里 | 怎么改 | 不改有什么影响 | 验收条件 |
| --- | --- | --- | --- | --- |
| 优先：正式输出底色 | 用于提示透明区域的预览棋盘格，被一起输出进 MP4。是 SDK 输出边界问题 | 区分预览网格、不透明成片底色、透明格式；让正式不透明导出使用明确背景，不强制裁满 | 文件成功、交付成功，画面仍不符合预期 | 横竖图、contain、位移、透明 PNG、多镜及透明输出逐项检查实际成片；日常 SDK 版本另核对 |
| 优先：混合确认状态作品 | 旧作品可能确认了一半。当前全确认接入要求全部准确确认；未确认导入又拒绝任何已确认镜头。是承接能力缺口 | 按稳定镜头逐项分类：确认且证据完整的保留原采用，未确认的转输入／候选，失效／歧义列问题。一次事务登记来源与结果，不把确认过的整体降级 | 这些作品还无法完整走当前接入，旧写入口不能全面退出 | 一单混合确认／待确认／跳过，保留准确轨 A、未采用 B；原确认、文件和未知请求保持，当前编辑后可导出 |
| 优先：原设置映射 | 原值存进来源档案，不等于当前工程已按它运行。是设置映射问题，不能只改名字 | 逐字段列「已作用到工程／仅预填／仅保留证据／不支持」。补口播和配乐增益、闪避、时间偏移、原声、裁切／构图、字幕样式和封面；不能用当前默认值覆盖原设置 | 接入可能保留素材，却改变原来的声音或画面效果；用户难以确认是否真正原样接续 | 用非默认原设置对比接入前后实际工程及成片；不支持项明确提示并保留原始值 |
| 优先：实际 UI 接入 | 后端能读原计划／接入草稿，但现页面主要是已有工程接续，还没有完整来源选择流程。是产品入口缺口 | 显示来源版本、核验状态、接入范围和阻塞项；Owner 选择原生、HTML、计划或镜头工作版本。已有当前编辑优先；脚本变化显示差异 | API 能做，但日常用户容易选错来源或以为候选已采用 | 从实际页面完成读取、选择、确认、接入、编辑和重开；错来源／过期／当前编辑／其他 Owner 均拒绝 |
| 删除前：恢复矩阵 | 新接入记录多了不可变来源和当前引用。已有某个 SQL 函数的整库恢复，不等于所有作品连同文件均能恢复 | 对原生、HTML、保存计划、确认／未确认／混合绑定分别做整库＋文件、逐项、不同来源 Owner、同文件多引用、路径搬迁和中断恢复 | 平时制作成功，备份恢复时仍可能出现断引用，无法证明可撤旧链 | 精确 ID／SHA、原采用与未采用、脚本／镜头／轨关联一致；错 Owner、现编辑和冲突不覆盖，不能靠重发生成补齐 |
| 后续：大工程与复杂声音 | 多来源核验有开销，嵌套、变速等声音不能靠猜。是性能与覆盖问题 | 测大文件、多来源、多别名和超时，再决定是否按不可变身份缓存或分阶段核验；复杂结构逐项支持，不支持继续 unknown | 多来源保存的上限未证明，复杂声音统计仍有空白 | 记录实际耗时／资源上限；不得跳过 SHA、缩减保护或把未知值补零来换取绿色 |

## 名字能换到什么程度

| 范围 | 建议目标及做法 | 边界与成本 |
| --- | --- | --- |
| 当前通用模块 | `codexRunner`／`runCodexWorker` 可随实际职责改为 `mediaTaskRunner`／`runMediaTask` 等名称 | 更新导入、CLI、脚本、构建清单、prepared manifest、测试及当前文档。保留原包字节、任务与文件身份；中等改动，主要降低误读 |
| 共享 SQL | 当前 `claim_input_task → claim_input_task_pre_lease → claim_next_worker_task_legacy` 按资格／容量／资源／领取／lease 合并职责，再采用清晰名字；旧口播包装改成明确的旧协议拒绝边界 | 先列保护矩阵，再改实现／ACL／调用，不再堆一个新名字包装旧实现；结构改动成本较高，收益是可理解与可验证 |
| 当前制作身份／类型 | 当前 `preparationRevisionId` 仍可选，核心多处还用 `preparation_revision_id ?? storyboard_package_id`；适配后收紧为明确当前身份 | 真实数据转换、历史接入和恢复先完成；不能只用类型断言掩盖空值，不能直接全文替换列名 |
| 页面／原生素材显示名 | 用「镜头 01 口播」「配乐」等可读称呼；明确草稿、候选、当前已用的内容摘要 | 不重建 clip／轨 ID，不搬文件、不覆盖用户手工名称；局部 UI 改动即可，不需要重写后台 |
| 已持久化旧字段／枚举／JSON | 当前写入使用新协议；原字段只由版本化历史适配器理解 | 直接修改原 JSON、旧任务类型、SHA 输入或文件名会破坏恢复与冻结身份；必须版本迁移，历史原字节不改 |
| `Episode`／`episodes` | 仍是当前生产单领域实体，本身不是退役业务，不作为无用代码清理 | 如仍希望改为 `ProductionOrder`／`production_orders`，另做 SQL、外键、RLS、API、类型、备份与恢复迁移。成本大、主要是命名一致，建议最后决定 |
| SQL 基线与生成类型 | 从最终有效 schema 产出当前类型与新 clean baseline；历史格式声明分开 | 前向升级、新库与恢复一致后再生成；已应用迁移和 ledger 不改写，不靠重建基线绕开升级 |

可以把当前产品和执行层的旧名称彻底退下；不应把「旧名字必须完全消失」扩展成修改冻结证据或备份。真正的完成标准是当前代码无需依赖旧业务概念，而不是归档文件搜索 0 命中。

## 埋点的后续工作

本轮能同步联测，且相关路径没有发现重复计数或确认快照覆盖。当前制作步骤、声音使用、导出观察、受控请求／费用依据已具备，不需要重新做一套采集。

剩余工作是：为混合接入／更多设置变化／所有旧恢复来源补覆盖；复杂声音只在可证明时统计；多来源大文件做性能验收；提供明确的查询 API／Dashboard；最终版本一致后另做真实运行和启用前验收。真实供应商账单、GPU 和未支持结构继续保持未知，不能用估算或主机资源冒充实付／单任务消耗。

导入旧资料不能补造以前发生的采用或生成；本轮证明未确认导入不记为采用，之后 Owner 明确采用才记。停用期间不补造历史，统计错误不授权重发 Provider。最终日常部署、重启和采集开启仍按既定授权边界处理，本方案不执行。

## 建议实施顺序与每批完成条件

1. **修输出缺陷。**单独修 SDK 正式底色；通过实际文件和画面检查，不和 SQL 改名混在一起。
2. **补齐旧作品接入。**先混合状态、原设置、来源选择 UI，再做所有接入来源的完整＋文件／逐项／来源 Owner 恢复。已有当前工程优先，未确认不伪造确认，未知不重发。
3. **停止旧执行消费者。**发布新的执行合同，明确过渡包的退役范围；实际核对活动进程、编辑器和任务。日常切换另行授权，原包保留为证据。
4. **整组退役旧操作。**退出 v2 写命令、旧查询路由、七个拒绝签名、空扫描／旧预检和只服务旧业务的编排。用前向迁移准确 RESTRICT 删除，异常依赖应使事务失败，保留 Owner／权限检查和明确拒绝语义。
5. **收敛共享职责和历史边界。**旧批准／组包动作与校验拆开；领取、回执、预留用行为对比逐项保持。当前代码只消费当前模型，版本化旧解码器负责历史承接，不创造第二套执行内核。
6. **统一当前名称、类型和基线。**在最终边界上改模块、函数和显示名；当前执行目录加入退役标识禁用检查。先前向升级／新库／完整与逐项恢复对齐，再生成 clean baseline。
7. **最终联验和交付。**一次完整默认回归、相关完整集成、实际 UI、原生编辑／输出、升级／回滚／恢复、Owner／lease／费用／未知请求保护以及最终埋点对账。保存精确版本证据后再安排日常启用。

每批成功条件应包括功能允许／拒绝结果、原数据和文件保持、ACL／租约／冻结输入不变、幂等及中断恢复。备份之后若已产生新写入，不能简单覆盖旧库回退；每批要有可恢复的迁移和明确对账方法。

最终可以删的是无用执行入口、重复编排与旧兼容壳，可以换的是当前名称；应保留的是稳定身份、保护职责和原历史证据。本轮给出方案，没有实施上述改造。
