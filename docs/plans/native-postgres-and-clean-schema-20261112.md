## A/B：原生 PostgreSQL 方案

### 运行方式

建议 Mac 使用固定主版本的原生 PostgreSQL 17，优先评估 Homebrew `postgresql@17`，执行前核对适用补丁版；本次不同时升18/19。数据目录为项目专用私有目录，权限0700；端口仅绑定loopback。服务由项目自己的生命周期管理器按需启动和校验，不依赖随意启动的另一个全局数据库实例。

复用现有 SQL 与 `pg`，将现有 runtimeContext 的数据库操作集中为一个端口：身份核验、SQL、dump、restore及状态读取。原生实现调用已固定的PG工具；隔离测试实现调用受控容器。调用方不散落新的 `if native/if docker`，也不新建第二套业务访问方式。

原生身份校验需包括：规范数据路径、目录所有者/权限、实例标识、端口/进程/二进制版本、数据库名、角色与权限。继续保留 loop_app / loop_worker 的权限边界、Owner事务/RLS、任务租约/产物发布屏障和Keychain凭据引用。工具退出码、超时与错误脱敏沿用现有合同。

### 演练

1. 固定容器源版本、扩展、角色、权限、函数、任务状态、媒体/工程引用和schema ledger指纹；不把“数据行数相同”当作完整对账。
2. 改启动与工具适配后，在一次性容器中验业务SQL、角色/RLS、两任务并发及本机重任务互斥；不挂日常数据卷、不使用日常秘密、不请求真实供应商。
3. 在Mac单独临时数据目录/端口验原生启动、错实例拒绝、关闭/重开、dump/restore及故障恢复。Linux VM不能证明Mac原生生命周期正确。
4. 用逻辑导出/导入跨Linux容器与Mac原生迁移，不直接复制PG数据目录。角色/权限必须单独覆盖，`pg_dump`不包含完整集群角色。[PG17导出文档](https://www.postgresql.org/docs/17/backup-dump.html)
5. 核对行级内容指纹、主外键/序列、函数/触发器/权限、不可变蓝图/任务/候选/产物ID、凭据引用、幂等回执、租约与未知提交状态。验证正文/v2准备、图片/旁白/视频候选、字幕手工保存、Studio保存重开和受控交付。

### 正式切换与回退

- 切换前确认Owner已保存退出Studio，生产写入/任务消费者均静止，未知供应商提交/产物发布已核对；不能让新旧Worker同时领取。
- 制作本次迁移专用的一致性恢复包并验证可恢复。这不是启用周期自动备份；自动备份继续关闭。数据库凭据与Owner密码等敏感内容仅存受保护材料，不进入Git或普通日志。
- 最终一致性导出、恢复到原生目标、对账后，原子更新唯一数据库配置，只启动新实例的应用/Worker。先检查绑定及只读结果，再恢复正常写入；旧容器和卷保留为冻结恢复源，不继续写。
- 开放新库写入前可直接回退旧配置；开放写入后旧库已经落后，不能只改连接回旧库。必须再次停写、导出新库增量或完整状态并校验恢复，或按明确的截止点恢复，防止丢失新记录。
- 日常运行稳定后，Colima仅按需用于隔离测试，不自动删除其他profile、卷或镜像。彻底卸载Docker不是本计划目标。

## C/D：是否值得重整旧SQL

建议做，价值是减少历史技术包袱、缩短从空库建立的链路和降低Agent维护误判；它不直接提高视频生成速度。安排在原生化之后，符合用户希望的顺序。

“全部舍弃旧名称”建议限定为活跃schema、运行代码和当前配置。旧文档、迁移原文、冻结记录及旧供应商元数据归档保留；不通过字符串替换伪造历史。如果要求连历史记录中的名称也消失，会与保留历史记录冲突，需在实施前单独确定转换规则，本轮不做这类转换。

1. 以原生化后验证通过的有效schema为依据生成当前基线，逐对象审计旧schema/函数/触发器/权限/兼容表与真实调用者；不从旧基线简单删关键词，也不无审查地把全量pg_dump当作新设计。
2. 新基线与旧迁移分离。旧SQL移入历史归档，保留版本/SHA/决策链；迁移器新增明确的基线代际和旧ledger映射，避免它仍逐条查找已归档文件而拒绝运行。重复执行必须幂等，未知版本明确拒绝。
3. 当前业务表/API尽量保持稳定；退役专属对象有明确的依赖清单。保留原有拒绝未知服务、Owner隔离、冻结快照和产物发布约束，不能因为删除旧名称顺便删除保护。
4. 数据映射保留账号/生产单/版本/任务/候选/产物/凭据引用的稳定ID、内容哈希和历史状态；活跃旧服务不自动改为新服务，不重生成、不自动计费。唯一旧连接先归档确认其引用，不能直接丢弃。
5. 在不接日常库/秘密/媒体的VM中执行四条路径：空库新建；旧版本副本升级；旧导出恢复；升级后失败恢复/重跑。核对数据内容、权限、幂等、冻结快照、Worker=2且重任务=1、Studio/字幕/交付边界和秘密引用。
6. 通过后，再用相同转换迁到原生的全新目标数据库，不对正在使用的库直接大批DROP/改名。切换和回退继续采用B阶段的停写、对账和新旧单写者规则。

最新授权在本地分批提交完成后启动 C 的隔离阶段；在新基线验收及日常切换授权明确前，D 不执行。旧迁移、冻结记录及历史保护证据保留，不覆写历史。

## E：已认可、待统一实施的统计数据

优先复用当前任务/运行/产物/费用事实，补缺口；不重复采集所有点击，不接第三方埋点SDK。

| 数据组 | 最小记录与用途 |
| --- | --- |
| 生产单生命周期 | 创建、脚本确认、阶段进入/退出、实际交付完成；日/月产量、阶段与人工等待 |
| 任务生命周期 | 入队、领取、开始、终态、attempt、错误码、重试原因；排队时间、成功率、P50/P95 |
| 供应商请求 | 提交/完成时间、请求ID与结果未知状态；区分API等待与本机处理，轮询不计作新生成 |
| 候选采用与返工 | 生成、明确采用、明确放弃、返工原因；不把未采用直接当拒绝 |
| 费用 | 预留、结算、释放、估算版本与未知；预计/预留/实付分开，未知不当零，保留币种与精度 |
| 导出与技术质量 | 开始/完成、实际时长/尺寸/帧率/编码、校验结果；技术成功率和质量分档 |
| 资源与吞吐 | 槽位活跃、队列深度、CPU/内存压力和资源等待；按状态变化或采样，避免逐轮刷日志 |

共同维度：eventId、schemaVersion、UTC时间、Owner/账号/生产单/镜头/任务/请求/attempt ID、provider/model、项目质量档（与供应商quality参数分开）、资源类别。提交与事实写入同一可靠边界，重试按逻辑事件ID幂等，查询不产生新业务事件；失败/回包丢失不能重复计数。

同时统计墙钟耗时与累计槽位耗时；现有 `workerRunSeconds` 合并重叠时段，不能直接用作总槽位消耗。月度归属按Asia/Shanghai的实际交付完成时间，同时保留创建/月跨越情况。保留策略与聚合方式在实现时确定，不采集密钥、不为统计复制完整正文。
