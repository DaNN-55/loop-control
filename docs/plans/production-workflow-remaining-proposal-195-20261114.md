# 当前制作链与旧内容全面收口方案（195 副本评估）

日期：2026-11-14。状态：Proposed。此文只提出剩余方案，没有执行清理、重命名或修复；遵循 ADR-0066／0068／0069 的渐进替换方向。依据[本轮真实生产与埋点核查](../verification/production-replacement-assessment-195-20261114/REPORT.md)，不将旧报告中的缺失直接视为当前源码事实。

## 建议采用局部重构

保留已经工作的 Owner 事务、独立制作基准、原生工程、媒体执行和交付内核，逐段把旧格式和旧执行放到历史适配边界，再关闭旧执行入口、统一当前名称。无需整仓重写。

本轮两镜头新单已做到旧审核包／镜头草稿／审批零写入；v3、交付音轨身份、制作里程碑、口播和配乐使用事件已有实现，均不应重新安排从零建设。剩余问题主要是历史接入与当前核心混合、兼容合同尚未退出，以及导出观测的真实缺口。

## 先处理实际结果问题

| 优先事项 | 大白话与类型 | 怎么改 | 不改有什么影响 |
| --- | --- | --- | --- |
| MP4 留空区域出现棋盘格 | 预览装饰进入正式结果；输出行为问题 | 核对实际部署 SDK，明确普通 MP4 的工程底色，分开透明预览与正式渲染；用横／竖／透明图片、位移、contain 留空、多镜抽帧验收 | 文件和交付 SHA 都正确，画面仍可能不符合预期。不能用强制裁满代替修复 |
| 本机导出被资源采样漏掉 | 执行活动来源不完整；统计结构问题 | 以应用实例内、按 Owner 隔离的实际导出活动计数接入采样；成功／失败均 finally 清理；进程重启不遗留旧活动。采样使用独立连接，保留 Owner／运行时双开关 | CPU／内存高负载的一段反而可能无样本；只看 Worker 会误判空闲。主机指标仍不能归因成单任务用量 |
| 开始事件把独立导出串起来 | 开始统计在长事务中更新公共日汇总行；锁持有时机问题 | 执行前只捕获可信开始时间并登记活动，结束后随实际结果提交开始／结束事实。停用或跨覆盖时长明确未知；完整验证同 Owner 两单可同时进入执行 | 同统计分组的第二张单会等第一张提交。不能以取消幂等、Owner 检查或事务保护换并发 |
| 声音复杂编辑范围和保存成本 | 已实现基本使用，不等于任何 SDK 时间线都能精确判断 | 补环境声独立矩阵、嵌套变速、超调关键帧、转录剪辑；证据不足继续 unknown。实测大工程保存时文件核验／音频探测开销，缓存或复用须保留文件身份核验 | 复杂编辑统计不能声称完整；当前核验位于业务锁内，大项目保存延迟尚未量化 |

本轮单次导出约 5.52 秒不能作为性能目标；并发问题已实际复现，保存性能只是待量化事项，二者分开处理。

## 此前八类的当前处理

| 类别 | 现在的用途／问题类型 | 建议与删除条件 | 不改或误删的影响 |
| --- | --- | --- | --- |
| 1. 旧生成脚本链 | 已退役；没有新清理工作 | 保持归档，不重复安排 | 不应为追求旧词零命中而修改历史迁移 |
| 2. 旧批准后的初始化和复用 | `seed_shot_preparation_drafts_after_storyboard_approval`、`reuse_shot_preparation_history_after_storyboard_approval` 仍挂载；旧审批会隐式建／接草稿音轨。是业务结构问题 | 把需要的旧单转换集中为显式历史接入；验证原草稿、音轨、镜头身份及继承后，随旧批准执行退出删除。连同 `copy_shot_audio_mix_to_revised_draft`、`copy_shot_composition_to_revised_draft` 一起迁移验收 | 新单不用不代表旧作品不用；误删可丢混音／构图继承，保留则继续承担隐藏动作维护成本 |
| 3. 旧任务完成组包 | `create_storyboard_review_package`、`create_visual_review_package` 仍由 tasks 触发，混合结果验证和旧投影 | 保留有效租约、冻结输入、文件、回执验证；旧格式投影移入版本化适配器。确认原在途／未知／迟到结果有承接后，再删纯旧组包触发 | 只禁新领取不能处理已发出的请求；误删可能丢证据或破坏恢复，不能自动重发补救 |
| 4. 七个拒绝 SQL | 旧包调用时得到明确退役结果，是兼容门牌 | 先落最低执行版本门槛，再删除旧签名、消费者和陈旧类型；用明确签名及 RESTRICT，不 CASCADE | 提前删除会变成缺函数错误。不能同时要求原包原样执行且其签名完全消失 |
| 5. 空扫描与旧预检 | `script_production_scopes()` 返回空；`record_episode_worker_preflight` 仍做 Owner／时间登记，旧包仍引用 | 随旧包执行退出移除扫描、旧 Runner 和探测；保留当前能力就绪／连接／文件预检 | 不改主要多维护兼容合同；按 preflight 名字批删会误伤真实检查 |
| 6. 旧 v2 手动命令组 | 设置、暂停、绑定、旧审核渲染／交付仍有第二套 HTTP／业务链；功能重叠 | 原 HTML／原生作品经明确接入当前工作区后，退役六命令、旧查询、Runner 和 HTTP 入口；旧计划保持可读，未采用候选与未知请求保留 | 长期保留两套规则；直接删会让旧单失去编辑或交付能力 |
| 7. 共享 Worker／SQL 包装与旧名称 | 当前任务也走 `claim_input_task → claim_input_task_pre_lease → claim_next_worker_task_legacy`；`codexRunner` 仍执行媒体工作。兼有命名与职责叠层问题 | 先列资格／容量／公平／lease／attempt／冻结输入／文件／回执保护映射，再收敛重复包装并按职责命名；同步 SQL、ACL、CLI、prepared manifest、类型和导入 | 只改名主要改善理解，不能承诺提速；误删某层可能直接丢保护 |
| 8. 历史／冻结保护与旧字段回退 | 旧格式仍需读取，当前核心多处分支猜两代身份；结构边界问题 | 历史解码按版本集中，转换后进入严格当前类型；覆盖完整备份、逐项投影、旧源导入及冲突。`link_review_package_approval` 和过期口播失效触发器按关联／失效保护分别承接 | 保留分散回退会继续增加两代逻辑；删除关联／失效保护可能使旧任务重新有效。原证据必须保留 |

七个拒绝入口为 `plan_input_tasks`、`queue_workspace_planning`、`replan_workspace_planning`、`save_planning_selection`、`generate_input_shot_tts`、`apply_episode_configuration_repair_v2`、`apply_external_connection_repair`。六个旧手动命令为 `configureScriptProduction`、`pauseScriptProduction`、`applyScriptSettings`、`bindScriptVideo`、`renderScriptReview`、`prepareScriptPublish`，旧查询为 `/api/local/script-production`。

本轮有效 SQL 和原包清单确认这些边界仍在；没有把一条新单成功当作所有旧运行包与恢复格式均无依赖的证明。

## 当前模型、命名和界面怎样收口

| 部分 | 属于什么问题 | 具体改法与完成条件 |
| --- | --- | --- |
| 当前制作身份 | 合同尚未完全严格 | 当前 `ProductionWorkspace.preparationRevisionId` 仍可选，多个核心模块用 `preparation_revision_id ?? storyboard_package_id`。当前类型改为必填，当前核心只读独立基准；历史适配器核验同 Owner／生产单／来源后转换。不能只删回退表达式 |
| 历史数据类型 | 多代身份混在同一接口 | 当前工作区与各版本历史载荷分别建类型和解码器；冻结请求按原版本读取，不给旧快照补字段伪装当前请求；歧义进入只读／明确失败，不猜首条 |
| SQL 领取／回执包装 | 保护、派生和命名混合 | 按“资格选择、租约登记、冻结任务包、结果验证”梳理职责。可以收敛为少量事务边界，避免把所有检查塞进一个大函数。每次移层都有允许／拒绝结果对比 |
| `codexRunner` 等执行器名 | 名称与实际工作不符 | 可改为 `mediaTaskRunner`／`runMediaTask`，同步当前导入、CLI、构建清单和测试；原包字节不改。历史 HTML 渲染留在历史工程适配器，通用媒体能力继续复用 |
| 原生素材显示名 | 内部机器身份暴露给用户 | 页面展示「镜头 01 口播」等名称，用户手工命名优先；`workspace-narration-shot-shot-01`、UUID、路径、clip ID 和 SHA 不因此重建 |
| 草稿、候选与已采用内容 | 产品语义容易误读 | 各自表达当前草稿、可选候选、工程实际采用；保存草稿不自动替换成片，预览／交付取实际采用。宽窄 UI、拒绝后重开、改草稿后导出必须实际验证 |
| `Episode`／`episodes` | 现行领域实体，不自动等于废弃 | 可保留现行内部实体名；若要求当前数据表也统一成 `production_orders`，另做跨表／FK／RPC／API／恢复映射迁移。它不修复本轮缺陷，不宜夹在普通清理中 |
| 当前类型与 clean SQL | 有效运行结构和历史迁移并存 | 先完成前向迁移和最终有效 schema，再生成当前接口及新基线；对新建、升级、失败回滚、整库／逐项恢复做一致性对账。旧迁移、ledger、历史备份原样保留 |

“完全替换旧命名”可定义为：当前界面、当前模块及当前公开执行合同不再借旧流程概念表达。历史 JSON 的字段名、不可变原包、文件身份和归档迁移继续保留原字节；追求全仓库搜索不到旧词会破坏可恢复性。

## 埋点还缺什么

基础声音使用与本机导出生命周期已有实测，不能再写成尚未开始。尚需完成：

1. 导出活动、资源覆盖和并发修复，以及失败／拒绝／覆盖期开关／崩溃时的精确合同。没有结束事实的开始不能自动算失败；停用期间不记录、开启不补造。
2. 完整素材语义。`candidate_adopted`、`sound_used` 和 `workflow_milestone` 是不同事实；若要“全部素材采用率”，必须先定义可见图片／视频、时间线实例、来源及分母，不能仅统计候选或累加两个事件。声音复杂编辑不确定继续明确 unknown。
3. 只读统计入口／展示。当前 `readProductionMetricsV2` 有汇总，但尚无完整 Dashboard／统计 API。页面要解释停用缺口、等待时间、未知费用和统计窗口，按上海日期及不包含结束日的合同查询。
4. 最终冻结版本后的长期资源采样、重启连续性和启用前验收。当前测试证明受控响应下请求／回执／幂等保护，不能证明真实供应商账单或 GPU 用量。

## 分批实施顺序

1. **修实际输出与导出观测。** 优先解决棋盘格、资源漏采和日汇总行锁；补并发、开关、失败和崩溃反例。不以全仓改名夹带这些行为变化。
2. **完成当前合同和历史接入。** 当前必填独立身份，历史集中解码，逐项验证旧 HTML／原生工程、原草稿音轨、候选和采用证据。已有当前制作内核不重写。
3. **退出原运行包执行权。** 23 包逐一划分当前可执行、只读恢复、明确拒绝；在启动前说明版本不受支持，保留原包为恢复证据。未知／在途请求先核对，不自动重发。日常升级和必要重启另按授权执行。
4. **删除成组旧入口。** 门槛成立后退役旧手动命令、七拒绝 SQL、空扫描／旧探测及纯旧触发写入；有用的回执／审批关联／失效保护先迁移承接，再删旧壳。显式签名删除，额外依赖应阻止操作。
5. **统一当前命名和界面。** 先明确职责再改名，SQL／ACL／类型／构建清单／测试同步；显示名不改变冻结 ID 和文件。不会把纯命名工作描述为性能优化。
6. **生成最终类型与基线，完成总验收。** 新单端到端、全部历史格式与恢复、最低版本门槛、权限／租约／费用／未知结果、完整默认套件、真实 UI、有效 SQL 对账均通过，才宣布全面收口；日常采集独立启用。

验收目标是：一套当前制作模型与执行入口，新单不写旧审核／草稿／审批；旧作品可读、需编辑时可接入；旧包能否执行有明确结果；所有共享保护保持等价；当前名称表达真实职责。原历史仍存在是设计目标，不属于遗漏清理。
