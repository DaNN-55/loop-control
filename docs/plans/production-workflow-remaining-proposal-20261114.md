# 当前制作链剩余替换方案

> 后续状态更新：当前已新增193制作里程碑、默认v3入口。最新固定源码生产单与剩余判断见 [193核查方案](production-workflow-remaining-proposal-193-20261114.md)。本文件保留当时192评估，不当作最新实现状态。

日期：2026-11-14。状态：Proposed。本轮只做隔离生产、核查与建议，不实施下列代码、SQL 或命名修改。依据 [本轮报告](../verification/production-replacement-assessment-20261114/REPORT.md)、ADR-0066／0068 和当前固定源码；原 [完整实施规范](../specs/current-workflow-replacement-20261113.md) 的未完成范围保留。

## 结论与目标

建议继续分块替换，不整仓重写。独立制作基准、稳定镜头、字幕和口播输入已经有实际实现，新单能不写旧审核包就完成制作；推倒这些重写，会重复承担权限、文件、费用与恢复的验证成本。

目标应是「当前制作只有一套业务入口与数据合同，旧资料只经过明确的历史适配器读取或接入」。能清掉的是无消费者的旧执行入口、重复业务和多余包装；仍有用途的保护应迁入当前实现。历史文件、原包、旧迁移、旧音轨和冻结快照保留原字节，不为清除旧词改写它们。

当前页面、接口、类型及运行实现的旧名称可以替换。要求所有旧程序继续原样执行，同时删除它们调用的旧 RPC 名称，两者不能同时满足；应先建立明确的运行版本门槛，再退出旧执行合同。

## 生产单另外暴露或确认的事项

### 1. 优先处理成片背景：是输出行为，不是旧命名

本轮原图没有棋盘格；实际 MP4 的画幅空区却出现棋盘格。固定测试 SDK 的 `TimelineComposition` 使用棋盘格背景，导出 Root 默认 `transparent:false`，说明预览背景和成片背景尚未分开。`contain` 产生空区是本单主动选择，第一镜横向偏移也是本次原生编辑；应处理的是空区如何合成，不能靠强制裁满来掩盖。

建议明确项目／导出的背景合同：预览可使用棋盘格；普通 MP4 使用明确底色；支持透明的输出另走明确格式与合成配置。改动主要属于 SDK 渲染组件及集成边界，不能只改外层导出按钮文案。核对最终实际使用的 SDK 版本后再实施；本轮现象证明的是固定测试 SDK 的行为，未检查日常 SDK 是否相同。

验收用横图、竖图、透明图、画面位移和多镜头抽帧；普通成片不得混入预览装饰，预览和实际构图一致。现有文件、时长、声画和导出确认检查继续保留。不改时，素材未铺满画幅就可能把棋盘格当成画面交付。

### 2. 默认脚本与入口：后端已支持 v3，示例仍停在 v2

本轮新单用 v3，不含视频提示词也能完成。当前 `productionScriptTemplate` 仍是 v2，并预填视频模型与视频费用字段。问题是默认输入和后端能力没统一，不是需要重写脚本引擎。

将当前模板、帮助示例和页面导入改为 v3，明确图片／视频／现有素材／暂未选择；只在实际提交视频生成时要求视频参数。旧 v2 留在版本化解码器，结构化格式错误仍明确拒绝，不退化为普通正文。

验收默认下载模板后纯图片制作、混合来源、缺字段／未知版本，以及旧 v2 接入。不改仍能手写 v3，但日常默认路径会持续传递旧的视频优先观念。

### 3. 当前类型与历史回退：先统一含义，再移除旧字段

当前工作区返回 `preparationRevisionId`，类型仍把它声明为可选；多处业务仍有 `preparation_revision_id ?? storyboard_package_id`。这说明调用方还在同时解释两代身份。

当前类型要求独立基准必填；历史解码器负责把旧审核包转换为经过验证的独立基准，无法确定时返回明确的只读／不可接入状态。当前核心不再自行猜旧字段。旧冻结任务保留原协议，由版本化 Worker 解码，不能补写字段伪造成新请求。

验收缺引用、未知协议、跨单、伪装旧格式及新旧请求回执。不改主要增加误接身份和维护分支的机会；不是已经证明当前样例产生了错误。

### 4. 名称与草稿：先改显示，再整理实现名

本轮工程素材名称实际仍有 `workspace-narration-shot-shot-01`、`workspace-narration-shot-shot-02`。建议显示「镜头 01 口播」「镜头 02 口播」，保留用户手改名称；草稿、未采用候选与实际采用的内容清楚区分。正文和预览、交付始终依据实际采用证据，不因保存新草稿自动切换。

显示名称可改，内部素材 ID、clip ID、音轨 UUID、文件路径与 SHA 不需要跟着重建。执行器 `codexRunner`／`runCodexWorker` 等按实际职责改成通用媒体任务名称；历史解码明确带版本。候选名称应随最终职责确认，不能只做字符串替换。

`episodes` 是当前项目领域实体的现行名称，不单凭英文判断它属于退役流程。若仍希望改为 `production_orders`，应另列跨表、RPC、API、JSON 和恢复映射迁移；对本轮发现的问题没有直接修复收益，不建议纳入第一批。

验收实际宽窄界面、原生素材名称、保存重开、用户名称保持及原包读取。没有 UI 实测前不能只凭改了字符串宣布体验完成。

## 推荐执行顺序与删除门槛

1. **先修输出并收口当前合同。** 分开成片／预览背景；完成默认 v3 模板、当前必填类型及历史适配边界；保留已经实现的独立制作模型。验收本轮生产单再加背景和混合来源反例。
2. **补齐恢复和旧作品接入。** 针对真实格式继承、局部新增镜头、共用音轨、旧 HTML／原生工程、缺失／冲突／跨 Owner、在途未知请求做矩阵。原计划只读，旧作品可通过当前工作区操作；不改原证据、不自动重发。
3. **落实运行版本门槛。** 当前支持清单仍标记到 186，23 个原包均为 `compatibility-contract-retained`；源码已到 192，清单不是最新版兼容证明。逐包定义「允许执行／只读恢复／明确拒绝执行」，在启动或领取前检查，原包字节保留。
4. **删除成组旧入口。** 前述门槛通过后，清理六个旧手动命令与查询、七个拒绝入口、空扫描器／预检、无消费者的旧批准触发器及纯旧审核组包。用 `DROP ... RESTRICT`，额外依赖必须阻止清理；同步移除调用和陈旧类型。
5. **整理共享保护与名称。** 逐条映射 Owner／RLS／ACL、当前脚本、历史与回收站栅栏、容量公平、资源、attempt／lease、费用确认、发送事实、未知与迟到回执、文件与精确导出保护。按职责收敛 SQL 包装，之后改名；任何等价性不明确的检查先保留。
6. **补埋点并形成新基线。** 里程碑、声音使用、本机导出和可读名称随对应模块完成；最后从有效 schema 生成当前类型、生成与前向升级一致的 clean 基线。完整备份、逐项恢复、前缀升级、失败回滚、默认全套测试及真实 UI 验收全部完成后，才可称「当前旧执行链替换完毕」。

每批保持可独立验证；失败时恢复该批代码／数据库候选，不回写历史 ledger、不覆盖后来用户编辑。保持 Owner、费用、未知结果、文件与恢复保护作为硬条件。

## 如何确认已经清干净

不是搜索 `legacy` 得到零行，也不是删光旧迁移。最终应同时满足：

- 当前业务只写独立制作模型；新单无旧审核包／旧镜头草稿／旧审批，所有画面、口播、字幕和声音来源有明确基准身份。
- 当前 HTTP、Worker、SQL 和生成类型无退役执行消费者；旧运行版本得到明确支持结果，无“函数消失后自行重试”的路径。
- 共享保护有逐项等价验证；旧工程可读、必要时明确接入，当前与旧格式完整／逐项恢复均通过，原文件、原音轨和冻结证据保持。
- 当前实现与用户可见名称不再借用旧审核／旧自动编排术语；旧词仅存在于按版本隔离的历史解码、不可变证据和归档。
- 生产单、事件流水和输出画面一致；全套、UI、恢复及故障验收通过，未验证部分不冒充完成。

上述方案没有在本轮执行。日常发布与采集启用也没有执行。
