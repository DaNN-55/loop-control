# 当前制作链全面替换方案：来源选择专项复核后

日期：2026-11-14。状态：建议，未执行。依据本轮固定的未提交源码、当前有效 schema 至 197、独立新生产单与埋点联验，以及来源边界反例。关联报告见 [本轮生产单与核查报告](../verification/production-replacement-source-audit-20261114/REPORT.md)。原有 A–G 实施进度由原计划管理，本方案不将局部通过计为整体完成。

## 结论

建议保留现有四步制作、原生编辑、Worker、导出和交付内核，分批替换仍承担旧业务的入口与模型边界。无需整体推倒重写。最值得先做的不是全文改名，而是补齐「到底从哪个原版本继续」的统一规则、页面入口和恢复能力，再撤下第二套旧操作，最后统一当前名称和 SQL 基线。

当前源码已经比早期八类报告前进：新单采用独立制作基准，不再必须创建旧审核包、镜头草稿或审批；保存计划、原生／HTML、确认／未确认混合来源及多段构图已有接入实现。早期列出的交付音轨错选、历史脚本关联、纯视频脚本约束等不能不经核对继续当作未修问题。已有能力仍须完成所有来源、设置和恢复矩阵后，才能据此删除旧业务。

## 本轮优先问题

| 优先级／部分 | 大白话说明、问题类型 | 怎么改 | 不改的实际影响 |
| --- | --- | --- | --- |
| P1：脚本确认绕开来源选择 | 页面已经知道有旧保存计划，确认脚本的回调仍直接发 `prepareWorkspace`。属于操作时序与入口规则不统一，不是等待不够或命名问题 | 首次读取、确认回调、重试使用同一来源决策；来源未读完、读取失败或存在待核对原版本时，等待明确选择。无旧来源的新单仍可本地准备。脚本／生产单变化后丢弃过期结果；不重发未知命令 | 用户尚未选原版本就建立新工作区，后续接入又因已有工程被拒绝。原资料没有被删，但接续路径走偏 |
| P1：保存计划未遵守原工程优先 | 已有登记的 HTML 工程产物，来源列表仍只给计划；直接计划接入返回 200。属于后端一致性缺口，不能只靠前端隐藏按钮 | 后端统一原生工程、完成的 HTML／JSON、保存计划、镜头工作版本的优先级；有原工程但文件或来源不可核验时给明确阻塞，不静默从低级来源重建。明确另建版本如有需求，应设计独立操作，不暗中替代 | 旧剪辑仍留在原文件，但当前工程可能由较早计划重新构造；用户易误认为原编辑已经完整承接 |
| P1：正式导出背景 | 隔离 SDK 将编辑器透明棋盘格用于非透明输出。属于输出边界缺陷，与 SQL 清理无关 | 编辑预览网格与正式成片底色分开；导出按明确背景／透明策略渲染。检查 contain 留空、旋转、分屏空位、图片和视频；实际抽帧验收 | 文件检查、SHA 和交付可全部通过，成片仍可能带编辑辅助网格；不能靠把所有图裁满来掩盖 |
| P2：统一来源选择 UI 尚未完整 | 类型支持四种来源，服务端当前只枚举保存计划；旧原生／HTML仍有分散接续按钮。属于产品入口与后端能力没有收口 | 同一处列原版本、脚本基准、可用／阻塞原因和接入范围；当前工程优先。选择下拉框只选择，显式按钮才接入，后端再次验证。已确认内容保留原采用，未确认只导入输入与候选 | API 能做的事，页面未必能完整表达；用户需知道旧入口，维护者继续维护两套操作 |
| P2：原声意图、封面及全设置映射 | 部分增益、闪避、字幕、转场、裁切和构图已实施，不能再一概称为丢失；剩余字段需逐项对账。属于数据语义映射 | 为每个来源列原字段→当前字段→原生效果→恢复断言；已采用与未采用分别处理。无法表达的原值保留证据并明确阻塞，不伪造成默认值。当前人工编辑优先 | 原记录虽然还在，接入后的成片未必体现所有原意；「已备份」不等于「已生效」 |
| P2：完整恢复覆盖 | 一条原生来源恢复成功，不等于保存计划、HTML、混合草稿都能连文件恢复。属于跨数据库与文件的集成验收 | 每种来源分别做整库＋文件、逐项、来源 Owner、同文件多轨、路径迁移及中断；恢复后实际打开、编辑、导出并核对原 ID／SHA／采用状态 | 平时能制作，恢复时可能缺引用或无法接续；不能以重发生成来补齐 |

小单通过不能证明大工程的性能上限。后续应测多来源大文件、重复引用和超时，记录真实读取／校验／保存／导出耗时，再决定是否按不可变身份缓存或分阶段读取；不能跳过 SHA、放宽源长或减少权限检查来提速。

来源优先级须由后端统一，而不是只改变展示排序。当前已存在工作区始终优先，任何接入不能覆盖它；不可读原工程必须保留为可解释的阻塞项。新来源不继承旧预算、连接或外部请求授权。

## 此前八类如何处置

第 1 类已清理，不重复安排。

| 类别 | 当前用途与问题类型 | 完全替换的方法 | 保留原因／不改影响 |
| --- | --- | --- | --- |
| 2：批准后建草稿、历史复用、继承设置 | 初始化／复用、音量／构图继承仍挂旧表触发器，相邻裁切继承也在；动作藏在数据库。是隐式业务与旧模型耦合 | 必要的原采用和设置继承收进版本化历史接入边界；退出旧审批／旧草稿写入后，按实际依赖撤下纯旧触发器及函数。冻结、引用锁和输入失效保护另行承接 | 暂为尚未全面承接的旧来源保留。长期代价是理解成本；直接删会漏掉设置或历史复用 |
| 3：旧视觉／分镜完成组包 | 完成触发器仍同时核验冻结输入、结果与文件，并登记旧审核证据。是保护职责和旧业务混在一起 | 将 lease／attempt／输入／实际文件校验保留在共享回执边界；旧格式结果由历史适配器解释，已退出的自动组包动作单独撤下。测试正确迟到回执与假哈希拒绝 | 旧任务不能领取，不代表迟到结果可不校验；误删会丢证据或接受错结果 |
| 4：七个退役拒绝 SQL | 旧规划、旧旁白、旧配置／连接修复签名明确拒绝；本轮当前执行源码／其他有效函数体未找到精确调用。是兼容合同 | 先确定最终执行协议和实际消费者退出；更新运行包与启动探测，前向迁移按准确签名 `RESTRICT` 删除，清理当前类型／声明。原包保留归档 | 没有证据表明会自动恢复旧生成。暂留是旧包／动态消费者退出条件尚未全部验收，不是七套功能必须永久保留 |
| 5：空扫描器、旧 Worker 预检 | `script_production_scopes()` 为空阻止旧自动发现；预检函数写旧记录。是两种不同的停用／兼容职责 | 分别随旧扫描器与旧预检消费者退出删除；当前文件、目录、连接、资源、运行版本检查继续保留 | 多一些合同维护；把空结果改回真实结果会恢复旧行为，按 preflight 批删则可能误伤共享保护 |
| 6：v2 六个手动命令及旧查询 | 后端仍有保存关闭计划、暂停、应用设置、绑定、渲染、交付和 `/api/local/script-production`；新来源读取也仍复用 `ScriptProductionStore`。是两套业务并存 | 先完成统一接入 UI／原设置／恢复，再整组关闭旧写命令。原计划只读改放明确历史来源接口；后删旧路由、无用配置写入和类型 | 不改不会自动续跑，但长期维护两套规则。先删读取器会伤及当前来源选择，先删手动操作会让部分旧作品失去接续路径 |
| 7：旧 Studio／媒体与共享 Worker | 旧渲染编排仍有 SQL 调用；当前领取仍经旧名包装；旧口播预留包装仍作为拒绝边界。是共享结构与命名混合问题 | 旧渲染随接入替代后退役；共享领取／预留／回执按资格、公平、容量、资源、attempt、lease、持久发送事实收敛为明确事务实现，再改职责名。禁止只加一层新名字套旧实现 | 当前仍需这些保护职责；盲删影响任务领取或费用／未知结果处理。单纯改名没有已证明的速度收益 |
| 8：历史、冻结及版本化格式 | 原脚本、草稿、音轨、任务、审批、SHA、锁和归档 SQL 是恢复依据；当前核心仍部分识别两代身份。是协议边界问题，原证据本身不是垃圾 | 旧协议集中到版本化解码器／接入／恢复模块，当前内部逐步收紧为独立制作模型。稳定身份和原字节保留；当前读写退出旧字段后再处理不再需要的列和类型 | 不改增加分支与排查成本；删除历史／改冻结字节会破坏恢复。历史主脚本关联已有修复，不重复安排无依据的重写 |

第 2 类明确对象为 `seed_shot_preparation_drafts_after_storyboard_approval`、`reuse_shot_preparation_history_after_storyboard_approval`、`copy_shot_audio_mix_to_revised_draft`、`copy_shot_composition_to_revised_draft`，并连同 `copy_clip_segments_to_revised_shot` 复核。第 3 类为 `create_visual_review_package` 和 `create_storyboard_review_package`。挂载本身不证明业务必须永久保留，也不允许跳过保护职责直接删除。

## 旧名称能替换到什么程度

| 范围 | 建议 | 如何迁移与实际收益 |
| --- | --- | --- |
| `codexRunner`／`runCodexWorker` | 按当前职责改为 `mediaTaskRunner`／`runMediaTask` 等 | 静态导入、Worker CLI、构建／运行包 manifest 与测试同步更新。无需重写执行器，主要消除“仍生成脚本”的误读 |
| `*_legacy`、`*_pre_lease` 等共享 SQL | 先整理职责，再命名为明确的资格／领取／租约操作 | 逐项保持原子事务、公平、容量、RLS／ACL、历史／回收站栅栏；不是把函数体复制到新名字再保留所有旧包装 |
| 当前 `preparationRevisionId` 和旧审核 ID 回退 | 历史解码后只传严格当前身份，当前模型中逐步改为必填 | 需真实迁移、恢复和调用链收口。不能用类型断言掩盖 null，不能把不同 ID 全文替换成同一个名字 |
| 页面与素材显示名 | 用「镜头 01 口播」「配乐」「原保存计划」等用户词汇 | 原 ID／路径／SHA 不动，人工名称优先；局部显示层修改即可 |
| 旧 JSON 字段、枚举、产物类型 | 当前新协议停止写旧概念；历史解码器继续认识原格式 | 旧 `storyboard/v1`、A-roll／B-roll、冻结任务和备份字节不能原地改写。它们可留在历史边界，不再支配当前制作 |
| `Episode`／`episodes` | 仍是现行生产单实体，不作为退役内容批删 | 若坚持统一为 `ProductionOrder`，独立规划 SQL、外键、RLS、API、类型和恢复迁移。成本高，主要是命名一致，建议最后决定 |
| 生成类型与 SQL 基线 | 最终有效 schema 生成当前接口，历史格式另定义 | 前向升级、新库、整库及逐项恢复一致后生成新 clean baseline；已应用迁移和 ledger 不重写 |

完成标准应是「当前执行层只使用当前概念，历史读取有明确版本边界」，不是整个仓库搜索旧单词零命中。归档运行包、迁移及冻结证据中的名字保留，不妨碍当前名称完全替换。

## 埋点是否需要另起一套

不需要。埋点代码已在同一源码，可以随本次生产单联验。制作里程碑、声音使用和本机导出观察已经有当前实现；早期缺这三项的报告不能直接套到现在。

后续重点是最终版本和运行包一致性、各种接入来源／复杂声音／恢复路径的事件口径、长期与跨进程采样，以及查询 API／Dashboard。资源样本是主机观察，不是某任务独占消耗；费用预留、冻结估算、应用回报与供应商实付分开，未知继续为 null。导入不补造以前的采用，重复读取不多计，停用不补造，统计错误不能授权重发供应商。

本轮未验证真实图片模型、视频 API、真实供应商扣费、GPU 或正式部署。日常开启仍需针对最终代码／迁移／运行包做启用前验收，之后另行授权部署、必要重启与采集开启。

## 推荐实施顺序

1. 修本轮两个来源入口缺口，单独修正式输出底色；先保结果正确与操作明确。
2. 补齐统一来源选择、剩余意图／封面／设置映射，以及各来源的真实恢复验收。当前编辑和原确认优先，未确认不伪造采用。
3. 发布最终执行协议，核对并退出实际旧应用／Worker／编辑器消费者；保留归档包。当前 v5 入口拒绝完整 v4 原包，不等于已经停止所有旧进程。
4. 退役六个旧手动写命令、旧查询路由、七个拒绝签名、空扫描器／旧预检及纯旧渲染编排，使用前向迁移和明确依赖失败。
5. 将共享领取、回执、预留整理为少量清晰实现，把旧格式限制在历史适配器；逐项保留权限、租约、冻结、费用和未知结果保护。
6. 统一当前模块／函数／显示名，收紧类型，最后生成新的有效 SQL 基线。
7. 对最终整体运行完整回归和实际 UI、导出、升级／恢复、埋点验收，再安排日常切换。

每批都应有正向制作、错误 Owner／SHA／lease 拒绝、幂等、崩溃／中断恢复、原数据／文件保持和新旧 schema 对账。数据库切换后已经有新写入时，不能简单覆盖旧备份当作无损回滚。

可以最终删除的是退出消费的旧执行入口、重复编排和纯兼容壳；值得局部重写的是交织的来源决策和共享包装；适合直接改名的是通用执行模块与显示文字；必须保留的是当前保护职责、稳定身份和历史原证据。
