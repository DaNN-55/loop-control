## Supabase 替代评估

### 当前依赖与替代方式

| 当前职责 | 已确认事实 | 本地替代方向 |
|---|---|---|
| 业务数据库 | 32 张业务表，包含版本、审核、任务与产物索引 | 本地 PostgreSQL；SQLite 为高改造量选项 |
| 业务规则 | 大量数据库函数、触发器、事务与约束 | 首先保留 PostgreSQL 语义，再逐步整理业务服务 |
| 身份与权限 | Supabase Auth、RLS；本机接口也远端验证 Owner | 本地 Owner 会话与 API 权限，保留账号隔离 |
| 任务领取 | 行锁、分组锁、事务领取、尝试次数与租约 | 本地事务与统一调度队列 |
| 外部连接密钥 | 实际依赖 Supabase Vault，Worker 通过 RPC 解析 | macOS Keychain 或本地加密存储，保持连接版本引用 |
| 媒体产物 | 大部分已在本地媒体库 | 保留本地文件与索引校验 |

前轮没有发现核心生产路径依赖 Supabase Storage、Realtime 或 Edge Functions。不存在只能由 Supabase 实现的核心业务功能；迁移难点是承接已有业务语义，而非简单替换连接 URL。

必须保留历史迁移和数据库测试。不要为瘦身删除历史迁移，也不要把已有状态机、审批、快照、约束当作可丢弃的云平台细节。

### 方案比较与当前建议

| 方案 | 相对成本 | 判断 |
|---|---|---|
| 本机自托管完整 Supabase | 相对较小，但运行组件较多 | 可作过渡，不满足彻底摆脱 Supabase 的目标 |
| 本地 PostgreSQL + 本地应用服务 | 中等至较大 | 当前推荐；保留 SQL、事务与锁，逐步移除 Auth、REST、Vault 等依赖 |
| SQLite + 重写业务服务 | 最大 | 最终运行简单，但需迁移 PL/pgSQL、RLS、锁等，不推荐作为第一步 |

候选目标：浏览器 → 本地应用服务 → 本地 PostgreSQL / 统一任务队列 → Worker → 本地媒体库；密钥进入本地秘密存储。

这是建议，尚未获批。实施前需写 Proposed ADR，说明如何承接现有身份、账号隔离、连接版本、任务领取与故障恢复；与既有 ADR 冲突时明确提出替代决定，不能静默改写契约。

### 性能证据与不能承诺的收益

前轮用真实 API 读取一条很小的 accounts 记录：

- 新建 HTTPS 连接的五次请求约 833–1275 ms，中位数约 937 ms。
- Node fetch 连续六次约 925、941、754、387、373、383 ms；后几次约 0.37–0.39 秒。
- 这包含网络、TLS、网关、数据库等端到端耗时，不是纯 SQL 耗时，也不是完整页面测量。
- 生产单详情最多 18 个请求，分三轮；有任务等条件下每 10 秒重新加载。摘要及部分列表还存在全量 select 和前端分页。
- 本地化预期首先改善打开页面、保存、审核、领取、写回和状态读取；模型生成与视频计算本身不会同比例提速。

不能承诺整单加速百分比。计算方法为：原数据库等待占比 × 该部分耗时减少比例。例如数据库等待占 20%、迁移减少该部分 95%，总时间才减少约 19%；这只是计算示例。

历史完成任务中位数参考：Codex 分镜 159.4 秒（11 条）、WhisperX 对齐 41.8 秒（12 条）、OpenChatCut 审核渲染 103.7 秒（3 条）、Google TTS 3.1 秒（15 条）、火山 TTS 4.2 秒（27 条）。包含开发历史，不可直接作为正式吞吐基准。旧 Hyperframes 与当前 OpenChatCut 记录不可混为同一渲染性能。

### 数据本地与完全断网的区别

- 数据本地：身份、业务状态、密钥、队列和媒体都在本机；Codex、云端图片、TTS、素材 API 可以继续联网使用。
- 完全断网生产：还需本地或人工替代 Codex、图片、TTS、在线素材，预下载 WhisperX 模型、字体和渲染资源，并验证质量、许可与实际速度。
- 完全断网是独立的可选后续范围，不能在迁完数据库后声称已经完成。
- 自托管 Supabase 可参考 https://supabase.com/docs/guides/self-hosting；开发 CLI 栈不等同于正式自托管部署。

## n8n 监测与轻量化

### 当前频率

| 机制 | 当前配置 |
|---|---|
| 任务派发 | 每 15 分钟 |
| 审核提醒 | 每 30 分钟 |
| 状态变更提醒 | 审核提醒调用的子工作流，无独立定时器 |
| 每日健康检查 | 每天 09:00，依赖 n8n 时区；启动脚本没有显式设置上海时区 |
| 页面系统状态 | 页面可见时每 15 秒 |
| 生产单详情 | 存在 ready/running 或追踪状态等条件时每 10 秒，可见时读取 |
| Worker 续租 | 每 5 分钟；过期回收阈值为 30 分钟 |

四条工作流在前轮本机检查时均启用。开始生产、部分镜头生成、审核视频已有即时派发，所以不是全部操作都等 15 分钟。定时器负责补漏及部分后续推进。

### 五秒可行性与代价

安装的 n8n 2.34.5 Schedule Trigger 支持 secondsInterval；项目 prepare-workflows.mjs 却将频率固定为正整数分钟，需要一起调整。只在 n8n 页面修改可能被下次导入覆盖。

- 15 分钟改 5 秒：每天检查次数从 96 变为 17,280，增加 180 倍。
- 每次启动都会编译 orchestrator，有任务时还编译 Worker；最新空闲检查约 8.38 秒，已超过 5 秒。
- 空闲发现最多四次远端查询，有工作时继续调用编排 RPC。提高频率增加请求、进程和执行日志。
- 常规模式的 n8n 不会自动提供项目全局并发保护；定时与即时入口可能重叠。
- 官方秒级说明：https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.scheduletrigger/
- 官方并发说明：https://docs.n8n.io/hosting/scaling/concurrency-control/

### 两种候选路线

短期保留 n8n：启动时或代码变更时编译；n8n 只唤醒调度服务；统一容量与防重入；用户动作即时触发、5 秒兜底；合并两类提醒；健康与备份分开；减少空闲成功记录。

长期本地化：推荐常驻本地调度器接管四条工作流，再移除 n8n。现有编排主体已经在 TypeScript 与 SQL 中，移除前需接回通知、备份、健康和可观测性，并修改启动与状态探测契约。不能直接删除生产 n8n 数据目录。

## 生产单并发与队列

- 当前没有固定的“最多 N 条生产单”限制；多个 Episode 可以同时位于生产、待审核和待输入等阶段。
- 同单内按依赖顺序推进，独立任务可并行；不同生产单不必等上一条整单完成。
- 单次编排批次的 Worker 默认并发 2；由 LOOP_WORKER_CONCURRENCY、CODEX_WORKER_CAPACITY 等决定。
- 数据库按 Provider + Adapter + 连接分组取 Provider/连接上限、Adapter 安全上限、Worker 容量的最小值。
- 默认容量 2 下：同组 Codex 为 1；Google/火山 TTS 为 2；Pexels 为 2（Adapter 上限 3）；多数图片、渲染、对齐及其他组为 1。
- 上述 2 不是全机统一硬上限：即时派发和定时派发可各自启动进程。真实稳定生产单并发数尚未压测。
- 当前每轮先等待一个已有任务，再规划并批量运行新任务，没有持续取空存量队列。若只靠 15 分钟定时器处理存量任务且无其他入口，推进可能很慢。

目标建议：所有入口只提交任务；一个调度器统一领取；槽位空闲即继续取任务；模型、下载、语音、渲染与对齐分别限流；不同生产单公平轮转；失败任务退避；先保守控制重型任务，再以真实样本增加容量。

## 正式使用前的已确认问题

### F1：备份清单过期且不完整

backupPolicy.ts 仍列出 experiments、metric_snapshots；前轮线上确认两表不存在，导出遇到不存在的表会失败。当前清单也未覆盖全部业务表。最近一次每日健康检查为 error；该执行记录未单独证明所有错误均由备份导致，不扩大归因。

修复目标：完整一致的业务数据库备份、独立密钥恢复方式、媒体备份范围与实际恢复演练。当前 best_effort REST JSON 快照不能当作完整可恢复备份。

### F2：过期运行任务回收路径断开

前轮线上函数定义显示，claim_next_worker_task 外层只筛 ready，再把该 ID 传给 legacy；legacy 内部虽能回收过期 running，却被这个 ready ID 限定，无法回收其他卡住任务。同组卡住任务还可能阻塞容量。

这是代码与线上函数定义检查确认的路径问题，本轮未做故障注入。修复应先回收过期租约，再进行容量核算与领取，同时验证活跃心跳不会被误回收、尝试次数与结果回写不串代。

### F3：缺少统一全局容量，启动开销与队列推进偏慢

定时、按 Episode 和按 Task 即时派发入口各自启动执行；默认批次并发不代表全机容量。每次编译、存量队列每轮仅优先处理一个、部分阶段等待下一轮，均影响响应。

修复方向：统一执行入口与常驻队列、编译移出调度热路径、容量和公平性管理、阶段完成后及时推进。

优先级说明：

- 首批重点是 BACKUP-01、LEASE-01、QUEUE-01、DISPATCH-01，以及相对独立的读取和渲染优化。
- “本地 PostgreSQL”是推荐选型，不能在批准前把它记作已决定；若 Owner 选择 SQLite，应重估迁移工作与事务锁替代，再调整后续任务。
- 若直接批准常驻本地调度器，N8N-01 的临时改造可以合并或跳过，但其通知、时区、日志要求必须由 N8N-02 承接。
- API聚合、界面合并、审批精简是不同任务，不要求为页面提速而先改变审核规则。
- 不预设能并行生产几条视频；先记录批次、资源组、全机容量三个层次，再从真实样本推导。
- 全部优化完成不自动授权合并。当前生产版本继续独立保留，Owner 最后决定是否切换。
