# 浏览器注释定向修复

用户在认可七个设置入口的统一布局后，要求使用子 Agent 修改最初四条浏览器注释。日期：2026-11-11。本轮只定向处理状态／操作反馈、资源可视化和 Owner 菜单；七个设置窗口整体迁移仍待审阅。连接与密钥的完整隔离交互继续保留在 5201。

## 范围与分工

- 状态与操作反馈：独立执行 Agent，负责当前阶段与真实阻塞的关系、具体原因、未知写入的只读核对入口及回归。
- 资源状态：独立执行 Agent，负责 CPU、内存、系统盘和素材盘圆环，保留原有量值及缺失语义。
- Owner 菜单：独立执行 Agent，负责横向溢出与长名称／邮箱，保留动作、键盘及低高度访问能力。
- 主 Agent：保留并行改动，核查关键结论、类型与集成、实际页面及交付边界。

不修改真实生产记录、不重发供应商请求、不清除未知结果、不提交或推送。原有日志、运行时及验证资料清理等改动不纳入本轮修复。

## 已核实的原因

“咖啡两镜头”的 `provider_result_unknown` 口播任务仍是有效阻塞，进入检查与交付并不等于解决它。界面只根据阶段给出“处理交付问题”，没有体现实际口播原因，是反馈缺口。

另一张生产单的红色提示来自写入请求的通用 503。现有证据不足以定位底层异常，不将较早的 Keychain、Vite 或数据库日志推定为这次原因。修复重点是说明原操作、提供只读工程核对，并保留结果未知语义。

菜单横向滑块来自共享分隔线的 `width:100%` 叠加左右边距，共超出 8px。Owner 专属修复应处理实际盒模型，而不是只隐藏横滚并裁剪内容。

## 验证与生效

### 实现

1. 工作台继续保留真实的「检查与交付 + 需处理」，状态下面显示「口播结果待核对」，当前作品列展示实际阻塞原因与「核对口播结果」入口。后台 `operationRows.blocker` 从对应生产单的 `task_blockers` 直接选取，不依赖另外分页的阻塞列表；旧响应仅在已返回的队列中找到同一生产单时回退。
2. 通用未知写入反馈说明本次操作，例如「打开剪辑工作台结果暂未确认」，提供「重新读取已保存工程」。这条动作只执行 GET；重读成功后仍明确原写入是否完成尚未确认。核对 A 未结束又启动操作 B 时，旧读取的错误和 busy 状态会被隔离，避免串到 B。
3. 资源区给 CPU 使用、内存非空闲、系统盘已用、素材盘已用添加圆环。容量原值、来源目录和同卷提示保留。无效或缺失比例显示「—」，未挂载不画旧值；不根据低 free 内存推断 macOS 内存压力，也不凭系统盘占用比例添加报警。
4. Owner 菜单使用专属浮层类和局部 CSS 修正分隔线盒模型。长名称／邮箱各自单行省略、保留完整 `title`，标准高度没有多余滚动；矮窗口保留必要纵向滚动，不裁掉退出登录。未修改共享 Dropdown。
