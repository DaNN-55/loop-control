# 旧生成脚本链退役验证

日期：2026-11-13。结论：两个目标均可退役，185 已应用日常；本组没有必须保留的目标函数。同步关闭通用 Owner SQL 中的旧生成脚本转换，防止删除触发器后出现空批准。历史数据、原脚本、草稿、音轨和冻结证据未删除，现有保护未放宽，不提交、不推送。

## 实际修改

- 删除 `public.create_script_review_package()` 及 tasks 上的 `create_script_review_package_after_task_completion`。
- 删除 `public.materialize_approved_script_revision()` 及 approvals 上的 `materialize_approved_script_revision_after_approval`。
- 在 `public.transition_episode(uuid,public.episode_stage,text)` 中，于原状态、Owner／会员、QC 和产物校验之后、任何业务写入之前，明确以 0A000 拒绝旧生成脚本阶段转换。保持签名、Owner、ACL、原搜索路径和其余函数正文；不新增前代包装函数。
- 扩展 schema 验证的精确退役对象清单，新增真实 PostgreSQL 集成；ADR-0065、PLAN 与本报告记录范围。其他七类只写分析，未执行结构或命名改造。

185 没有 CASCADE、历史迁移修改、数据 DML 或新增权限。当前手工正文／v2 确认与准备路径、视觉／分镜／QC／交付转换、旧视觉与分镜回执校验、原草稿与音轨复用、费用／租约／未知提交／文件确认和发布恢复保护保持。

## 调用链与删除依据

日常 184 中两个函数仅 postgres 可执行，各只有一个明确挂载触发器依赖，没有其他 SQL 调用者。当前执行代码与 23 个完整原运行包没有精确函数名引用；隐式触发事件另行验证，未以无名称引用代替安全结论。

当前制作使用已提供正文或 v2 脚本，不再创建旧生成脚本。当前领取资格排除 `draft_script`，原生回执允许列表也不接受它；46 个真实保存包 Worker 模块均使用该包装链，实际启动／领取／回执测试通过，旧任务未改变。直接公共结果函数也不向应用／Worker 角色开放，不能绕过原生入口恢复旧链。

真实导入 23 个原包的 Owner 命令模块：使用有效的原视觉包、实际文件、当前阶段和 Owner 会话，旧脚本批准全部被 400 或 410 拒绝；跨 Owner 请求保持 404。16 个旧版本仍能批准各自独立修订的真实冻结分镜，产生 16 条批准记录和 32 条镜头草稿，另外 7 个版本继续以 410 拒绝旧审核。没有新增制作任务、费用预留或 Provider 前置检查；原运行中生成脚本任务、实际媒体字节保持。

必须保留的相邻职责：旧视觉／分镜结果验证、旧分镜批准后的草稿初始化与历史复用、当前和旧包仍用的 Owner 状态转换、七个退役拒绝入口和空扫描／旧预检契约。它们没有因本次脚本链清理被删除或改名。

## 为什么需要明确拒绝旧脚本转换

完整私有反向变体只拆两对对象、不加入拒绝边界。原合法 Owner SQL 返回成功，实际状态是 `script_approved`、批准数 1、`main_script_revision_id=null`；严格的 0A000 拒绝断言失败，证明只 DROP 两个函数会导致错误的成功状态。

正式版本先保留原检查，再明确拒绝旧脚本转换，失败整笔回滚。原有效 Owner 的旧脚本批准／退回均被拒绝；其他 Owner 仍先以 42501 拒绝，未因退役泄漏数据或绕开归属。反向变体从未应用工作区或日常库，1 个预期失败及 1 个未选中用例不计为通过。

## 非空历史恢复与原保护

184 隔离夹具通过原完成触发器生成两份真实旧脚本审核包，其中一份通过真实应用身份批准并登记主脚本版本，另一份保持未批准；保存原任务／租约／运行包／结果、实际脚本文件及哈希、原 Prompt／审批／审核包和主脚本关联。同时保存已确认冻结 source 草稿、完成音轨、失败运行包、历史来源／版本／投影／共享文件／保护／留存及待处理回执。

完整 pg_dump 恢复后严格对账，再执行 185：

- 分别给两个函数加额外触发器依赖，均以 2BP01 阻止迁移；原有拆除动作随事务回滚。
- 注入 22012，全部改动回滚；正常迁移只删除预定两函数／两触发器和对应 ACL、加入精确的旧转换拒绝，新增一条 ledger，重复计划为空。
- 全部原行摘要、序列、角色、旧 ledger 和其余完整目录／权限一致。通用函数除明确的拒绝块外，定义与属性保持。
- 原 Prompt 内容篡改、冻结 source 草稿修改仍拒绝；原媒体、脚本及历史文件字节保持。未批准旧脚本不能经通用 SQL 获得空批准。

另外对实际历史投影器 `scripts/runtime/project-history.mjs` 做前后对比：从隔离业务副本移除待恢复的原生成脚本记录，再从保留的历史版本执行原投影。184 与 185 都实际插入相同的 12 条旧业务记录，保留原任务、批准、审核包、脚本版本和历史标记；所有业务／原历史行与投影状态一致，仅排除两次运行自然不同的 `applied_at` 时间。投影事务结束后复制角色恢复为 origin，普通保护继续生效。

**既有恢复限制：**测试同时复现了投影器先装生产单、后装脚本版本时，主脚本关联被提前判缺并置空、后续未补回的问题。原脚本版本与原引用仍在历史库，完整 SQL 备份恢复不受该逐项投影顺序影响。问题在 184 与 185 结果相同，本轮未修改投影器、未修改用户历史数据；不能把「未因本次退役产生恢复回归」表述成「现有所有历史关联都恢复无误」。详见 `remaining-eight-explained.md` 第 8 部分和 `projector-existing-limitation.json`。
