# 八类旧流程残留：是否值得改，以及不改的影响

检查日期：2026-11-13。依据是日常有效 SQL、当前页面／后端调用链、23 个原运行包和隔离恢复验证。除第一类获授权的退役工作外，以下都是建议，没有执行其他七类改造。

记录状态：第 1 类已通过 185 完成退役及日常验证；其余优化建议留待后续单独授权执行。本文保留问题、改法、影响与边界，后续实施前须重新核对代码、运行包和实际数据库状态。

## 1. 旧生成脚本审核与批准落库链

这是业务已经下线，数据库还留着自动动作的问题，不只是名字旧。过去任务完成时自动建立审核包，批准时自动把脚本登记成主脚本；现在使用的是手工正文或 v2 脚本的明确确认入口。两个目标分别是 `create_script_review_package()` 和 `materialize_approved_script_revision()`。

此项已清理，但执行时不能只删两个函数：通用状态迁移 SQL 原本还能接受旧脚本批准，拆掉落库动作后可能出现「批准成功，主脚本却没登记」。185 同时明确拒绝这类旧转换，保留原 Owner、状态、产物和其他审核检查，不改变当前手工脚本确认。

如果原样保留，不会因此自动恢复生成脚本，因为旧任务领取与原生回执入口已经拒绝它；实际代价是多一条容易误用的 SQL 路径，以及排查时要追的隐式动作。清理的主要收益是规则清楚，不承诺明显提速。

## 2. 旧分镜批准后的草稿初始化与历史复用

`seed_shot_preparation_drafts_after_storyboard_approval()` 和 `reuse_shot_preparation_history_after_storyboard_approval()` 会在数据库收到旧分镜批准记录时，自动建立镜头草稿、接回原素材与音轨。问题是动作藏在触发器后面，不看调用链会误以为没人使用；16 个旧包仍能走到这条链。

现在应保留。以后若要改善结构，可以先把这组动作收口为一个明确的兼容操作，再让旧 SQL 在同一事务里调用它，最后拆触发器；必须继续跑旧包审批和原音轨复用验证。仅把代码挪到新页面会漏掉旧包的 SQL 调用。

不改仍能正常兼容旧工程，不会因此多发起付费制作；维护时需要同时查审批、草稿和音轨触发器。属于可以以后整理的结构问题，没有证据要求现在重写。

## 3. 旧视觉／分镜任务完成后的审核包登记

`create_visual_review_package()` 和 `create_storyboard_review_package()` 的名字像旧流程，但现在还承担「以前已启动的任务把结果送回来时，核对当时确认的输入和文件，再登记原审核证据」的职责。旧任务不能重新领取，不等于原有效结果可以不校验。

应保留验证职责。最小改善是把职责和触发条件说明清楚、保留错误文件／错误哈希拒绝测试；如将来拆结构，应分清「校验原结果」和「登记原审核包」，不能在拆分时删掉校验。没有必要仅为去掉旧名字改公开契约。

不改没有已确认的功能问题，主要容易被下一轮扫描误判。删除则可能丢掉原审核证据，或接受与原输入不符的结果；此前对分镜触发器的反向实验已经实际检出后一种风险。

## 4. 七个已经拒绝执行的旧 SQL 入口

包括旧规划、旧输入旁白、旧配置／连接修复入口。它们像旧版本记住的门牌：门牌还在，但会明确回答「该操作已退役」，而不是重新安排任务。部分旧 Worker 的启动检查也查询这些签名。

这是旧版本兼容的成本，不是留下了七套可运行的旧制作功能。现在应保留名字和拒绝行为。以后先明确哪些旧运行包不再支持、核对启动与调用合同，再统一删除入口；可以维护一份入口与运行包对应清单，避免反复猜。

不改的代价是少量兼容代码和维护说明，未发现它们恢复了旧自动制作。直接改名或删除，会让旧版本得到未知入口／权限检查失败，而不是原来的明确拒绝；不能以移除 Owner 或权限检查来简化。

## 5. 空扫描器与旧 Worker 预检记录

`script_production_scopes()` 给旧扫描器返回空结果，让原来保存的「整期启用」记录不再触发自动续跑；23 个旧包引用它。`record_episode_worker_preflight()` 则在检查 Owner 归属后记录 Worker 预检时间，21 个旧包引用。两者用途不同，不能把「空结果」和「完全没用」画等号。

现在应保留。以后应分别处理：先停止支持旧扫描器，再移除空查询；先迁移仍使用预检记录的调用，再考虑合并或退役预检接口。改成一个大函数或统一改名没有明确收益。

不改主要是保留兼容维护量，不能据此推断有明显性能问题。把空结果改回真实扫描反而会恢复旧自动发现；随意删预检入口会打断旧包调用。

## 6. 旧 v2 手动制作命令组

`configureScriptProduction(false)`、`pauseScriptProduction`、`applyScriptSettings`、`bindScriptVideo`、`renderScriptReview`、`prepareScriptPublish` 以及旧计划读取仍在后端。当前页面没有调用这组六个命令，但原包包含它们；其中保存关闭状态、暂停以及手动操作仍然存在，启用旧自动续跑已被明确拒绝。

这是两代操作模型并存的问题，比名字问题更值得以后整体梳理。若要退役，先让旧计划可只读查看，并把仍需要的手动绑定、渲染和交付接到当前工作区，验证原文件、版本、审批与费用不变，再一次性关闭旧命令。不能只删页面上找不到的几个处理分支。

不改不会自动打开旧续跑，但后端需要长期维护两套概念，排错时容易混淆「当前分镜台设置」和「旧计划设置」。如果后续继续投入清理，这组业务边界比批量重命名更值得做。

## 7. 旧 Studio／媒体与共享 Worker 链

这一组混合了名字问题和真实复用：有些 `orchestrate_*` 仍安排旧工程的审核／最终渲染；`claim_next_worker_task_legacy` 仍在当前任务领取链里；`reserve_workspace_narration_submission_legacy` 则是当前包装层在遇到旧旁白路径时使用的拒绝边界。看到 `legacy` 或 `orchestrate`，不能一概判断成废弃功能。

现在应保留实际职责。优先写清调用关系和执行边界；如果以后仍频繁误判，可只重命名私有内部实现并同步调用者，保留公开入口和旧包契约。更深的拆分应按「当前任务执行」「旧工程接入」「拒绝旧请求」划清责任，而不是按文件年份搬家。

不改通常不会影响制作结果或速度，主要是维护者理解成本。盲目删除会影响真实领取、渲染、费用预留或旧请求拒绝；单纯改名也不会自动消除结构上的调用层次。

## 8. 历史数据、冻结保护与版本化 SQL

这组大部分不是技术债：旧任务、原脚本版本、审批、草稿、音轨、文件哈希、引用锁以及归档迁移，是证明「当时用了什么、批准了什么、如何恢复」的依据。旧定义仍在归档／基线中，不代表它仍存在于最终生效数据库；重建时还会按顺序执行后续迁移。

原记录、冻结保护和已生效历史迁移不应随清理删除或改写。可以改善有效对象清单、恢复说明和查询工具，减少把归档文本误当在用入口的情况。

但本次隔离测试实际复现了一个既有恢复顺序问题：历史投影先装生产单、后装主脚本版本；装生产单时只查询当时已装入的脚本，会把同一批中稍后才装入的脚本误判为缺失，并将当前主脚本关联置空，之后未补回。原脚本版本与原关联字段仍在历史库；完整 SQL 备份恢复不依赖这条逐项投影路径。退役前后复现与结果相同，未因本次清理新增。

这部分值得单独优先修，属于恢复关联问题，不是命名问题。可先按依赖装载父记录，再装引用；或先保存待恢复关联，等全部原记录装完后，核对原 ID、归属和冲突，再仅补齐缺失关联。不得覆盖当前已存在的主脚本，也不能为了补关联关闭普通用户的冻结、Owner 或引用保护。

如果不修，逐项导入某些旧生产单后，文件和原历史版本虽还在，当前视图可能没有正确的主脚本关联，需要人工核对。不能把「原始数据没丢」等同于「所有关联都恢复完整」。本轮只记录问题与方案，不修改投影算法或用户历史数据。

## 建议顺序

第一类已由 185 完成。后续优先独立修复第八类的历史关联恢复问题；其后再决定是否整体迁移第六类手动兼容业务。第二、三、七类先保持保护和合同、改善职责说明；第四、五类随旧运行包支持范围一起退役。上述后续优化尚未执行，没有依据做一次大规模改名或重写全部 SQL。
