## 两项新增来源反例

1. **脚本确认绕过来源选择。** 组件真实交互测试使用已读到保存计划的可写生产单，点击「确认脚本」后，实际命令为 `start → prepareWorkspace`；预期在 `start` 后等待 Owner 明确选择原来源。现有下拉框并未统一约束 `onConfirmed`。这不是等待不充分；断言记录到了明确的多余命令。该证据属于组件边界，没有冒称此反例已做真实浏览器复现。
2. **存在原工程登记仍可按计划重建。** 实际 Owner HTTP／PG 场景在同一单登记 completed 的 HTML 工程产物，读取 workspace 时仍只返回保存计划，直接 `adoptLegacyPlan` 返回 200 并建出保存计划来源的当前工程。原产物登记保留；没有发现原文件被删除。该场景没有提供可核验的原 HTML 文件和完整编辑契约，证明的是“不可核验原工程未阻止较低来源重建”，不能扩大成“已证明有效原 HTML 被覆盖”。现有草稿接入的 `requireNoRenderedLegacyProject` 已保守阻止这类重建，计划接入尚未统一。

两个安全预期均失败，未修改断言或产品实现来换取绿色。详见 原工程与计划回执（历史附件已清理：`evidence/original-vs-plan.json`） 和 反例结果（历史附件已清理：`evidence/source-boundaries-vitest.json`）。建议先修统一来源判定与确认时序，再扩大到所有来源的 UI 和恢复矩阵。
