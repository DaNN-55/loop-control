# 两处 UI 时序失败的根因修复与验证


> 产物清理记录（2026-11-18）：本目录的历史测试生成附件已按用户要求清理；本文验收结论保留。源测试输入、恢复资料、生产单和数据库未删除。

日期：2026-11-13。两处原失败均为测试等待不足；在受控异步边界与真实 Chromium 中，未改动的产品组件能完成预期功能。本轮只修改两个测试文件，未改生产组件、请求幂等、权限、SQL、超时或重试策略。没有提交、推送、日常迁移或重启。

## 根因及修复

| 失败 | 根因证据 | 最终修复 |
| --- | --- | --- |
| `LocalDeletionRecovery.test.tsx` 的目标任务焦点断言 | 卡片插入 DOM 后，React 的被动焦点 effect 尚可能未执行；原测试只等卡片出现就立即比较 activeElement。用真实 DOM 插入观察器可稳定复现 body 尚持有焦点的原错误 | 控制首次列表回包，在 React act 中交付；明确等待 activeElement 成为指定任务。保留只读、按钮、状态和不自动执行清理的断言，并补充后台刷新不抢外部控件焦点、显式更换目标时正确聚焦 |
| `WorkspaceNarrationPanel.manual.test.tsx` 的两次回执读取断言 | 重新打开时，已保存的候选本来就有「采用」按钮；按钮出现不能说明工程 GET 与冻结回执恢复已结束。原测试可在第二次回执请求发出前退出 | 覆盖即时与受控延迟两种回包。分别暂停工程读取和确认回执，断言等待期间候选禁用、未知意图保留、确认 POST 不重复；只有同一回执返回、登记区消失、持久 pending 标记清除且按钮恢复后才完成测试 |

没有靠增加固定 sleep、扩大超时、自动重试或删除断言获得通过。人工口播仍要求明确采用，没有自动采用；确认结果未知时仍只读同一冻结回执，保存及确认各一次，原 revision 为 3。新的完成条件也避免测试在请求／UI 收尾前结束。

当前产品在可控延迟下均正常，未发现这两种原症状对应的产品功能缺陷，因此没有调整焦点 effect 类型或放宽未知结果保护。前一测试遗留未结束请求是原过早结束可能造成的次生串扰风险，不将它当作已经证明的生产故障。

## 稳定复现与反向故障验证

在独立源码及原锁依赖中，不修改生产逻辑：

- 焦点复现使用真实 DOM 插入边界，保留原立即断言；回执复现暂停重新打开后的工程 GET，保留原「采用按钮已出现」判据。两次不可变受控执行均得到相同的 2/2 原失败，约 2 秒完成，见 `reproduction.json`、`reproduction-confirmed.json` 及日志。
- 仅在私有副本故意移除聚焦效果，修复后的两个焦点用例均失败，不能靠等待掩盖功能缺失。
- 仅在另一私有副本故意令未知确认重新发送 POST，即时／延迟两个回执用例均失败，能够检出错误重放。
- 故障变体的精确改动及 SHA 在 `mutations.json`，检测结果在 `fault-detection.json`；实际项目生产文件保持原字节。原受控红色夹具也私有留存。

一次复现尝试与文件更新交叠，不作为复现证据使用；随后在独立不可变红色副本确认双失败。没有把未隔离的结果计入结论。

## 真实浏览器验证

使用 agent-browser 的独立 Chromium 会话，实际装载原公开组件与真实 client／Web Crypto，通过合成 HTTP 边界控制回包，未访问日常页面或用户数据。

- 延迟列表返回后聚焦目标任务；后台重读不抢外部未禁用控件的焦点，明确切换目标能聚焦另一任务。无清理 POST。
- 浏览器原生禁用刷新按钮时会自然失焦，jsdom 不完整模拟这一行为；最终新增刷新测试使用不受加载状态影响的外部控件，区分组件抢焦点与原生禁用失焦，没有修改产品行为。
- 重新打开后候选可见，但暂停工程 GET 时仍未进行第二次回执读取，候选禁用；暂停回执时原未知标记和登记区保持；回执返回后标记和登记区清除。全过程保存／确认 POST 各一次，两次读取同一确认键。
- 另一次暂停超过原 10 秒回执期限时，实际出现 `signal timed out`，原未知意图继续保留；明确继续后第三次读取同一回执完成，没有新增保存或确认 POST。未修改超时。

结果见 `browser-focus*.json`、`browser-manual-*.json`、最终截图与快照。浏览器驱动及合成夹具留存为证据，不打包进产品；浏览器自动化中一次按按钮可见文本匹配失败、两次错误焦点等待已纠正为实际 aria 标签及不受禁用影响的控件，不计为产品失败。
