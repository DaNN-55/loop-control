`productionMetricsRetry` 旧夹具只设置历史 `storyboard_approved` 和旧审核包，没有当前入口要求的已确认脚本。它省略旧包 ID，191 默认入口按新作者准备处理，正确返回 403。新生产单通过真实确认后不出现该错误。

## 八项之外还应补齐什么

1. **剩余媒体快照统一。** Pexels 检索／预览仍通过 `queue_workspace_pexels_before_shot_protocol` 和新外层转换；其 Node target 包含脚本、工程、镜头，却未像新生成任务一样明确冻结独立制作基准引用。建议采用同一版本化基准身份，保留原连接资格、目标变化、预览来源和只读历史校验。本轮没有执行 Pexels，也不据静态差异断言它已经产生错误。
2. **类型与空值回退收口。** 多处仍使用 `preparation_revision_id ?? storyboard_package_id`。当前数据库已要求独立基准非空，应在历史解码边界处理旧来源，当前业务内只认 canonical 字段；这样能减少误把旧包当新基准的机会。不得回写旧冻结任务补字段。
3. **旧包支持清单需要更新为最终状态。** 现有清单保存 23 个不可变包，标注到 186，执行支持仍为 `compatibility-contract-retained`；本轮源码已到 191。清单是历史事实，不是自动证明 191 和全部旧包仍可执行。需重新验证或明确最低可执行版本，原包保留归档。
4. **测试也要表达入口用途。** 本轮暴露的重试夹具必须明确「新作者准备」还是「历史接入」。未来调整主项目测试应保留拒绝断言，不改成放宽脚本确认。

## 全面替换的推荐顺序

### 第一批：完成制作模型和恢复关系

把剩余媒体请求／回执、历史排版接续和逐项投影接到独立基准；当前业务只使用同一套镜头、字幕、口播和来源合同。新增表要同时纳入完整备份、逐项投影、版本选择和精确删除协议。

验收：新单不产生旧包／旧草稿；旧单接入不改原工程、原音轨和冻结证据；非空逐项恢复核对脚本→基准→镜头→输入→工程→候选／音轨的完整关系。重复恢复不覆盖当前编辑，冲突和跨 Owner／跨单引用拒绝。

### 第二批：迁走旧手动业务，建立旧包退出门槛

保留旧计划只读；把必要编辑、素材绑定、导出和交付接入当前工作区。对原包逐个标记继续支持、仅历史读取或拒绝执行；最低版本检查必须在启动或领取前给出明确结果。

验收：旧 HTML、原生工程和人工编辑能按支持策略继续使用；在途／结果未知请求可核对或收取既有结果，不自动重发。不是删除测试目录里的原包来证明兼容已结束。

### 第三批：删除整组旧入口与纯旧触发器

满足前两批后，候选包括：六个旧手动命令和 `/api/local/script-production`，七个拒绝 RPC，空扫描器、旧 Worker 预检，以及已无消费者的旧审批初始化／历史审核组包。逐条核对 SQL 依赖、触发器、Node、类型和运行包；只删除明确签名，不用 `CASCADE` 扩大删除。

验收：当前制作与历史读取、恢复不依赖它们；有额外依赖应阻止迁移；失败回滚、原行／权限／序列／ledger 保持。保留审计、已采用 SQL 和历史快照。

### 第四批：整理共享函数，再改当前名称

先把领取、资格、容量公平、资源、attempt／lease、费用预留、持久发送事实和回执验真逐项列成保护清单，再收敛包装。不要把所有逻辑塞成一个巨型 SQL 函数。

候选职责名称：`claim_next_worker_task_legacy` 迁为明确领取函数；`*_pre_lease` 按资格或租约职责合并／命名；拒绝函数要表达“不支持”；`codexRunner`／`runCodexWorker` 可改为通用媒体任务执行器。命名方案须跟最终职责一致，不能先批量替换。

### 第五批：统一入口、显示名、埋点和当前类型

默认示例切换 v3；素材显示「镜头 01 口播」等易读名称，保留用户手工名称；明确草稿和已采用内容。补齐制作里程碑、声音使用和本机导出活动，再生成当前有效接口类型。

内部 ID、已采用音轨、SHA 和文件路径不为显示名搬动。`episodes` 是项目现行领域实体，不因英文看着旧就必须改表；如确要统一为 `production_orders`，单列跨 SQL／API／历史映射迁移，其收益和成本另评估。

### 第六批：生成新 clean 基线，做最终验收

所有前向迁移稳定后，验证全新建库、旧前缀升级、非空完整／逐项恢复、未知请求／迟到结果／故障边界、UI 和完整默认套件，再生成与前向升级一致的 clean baseline。基线不是绕过迁移的捷径，原 ledger 不改写。

日常包更新、必要重启和采集启用属于后续独立发布步骤，本报告没有执行。

## 旧命名能清到什么程度

目标可以是：**当前页面、接口、类型和执行实现全部使用当前业务名称；历史读取集中在带明确版本的适配器。** 原快照、归档 SQL、旧备份和不可变原包里的旧名字继续保留，这是来源证据。

如果还要求全部旧程序原样运行，它们记住的旧 RPC 名称就不能同时彻底消失。要做到当前运行库无旧执行入口，需要明确停止这些原包执行，以当前恢复器读取旧资料；不能通过修改归档字节伪造兼容。
