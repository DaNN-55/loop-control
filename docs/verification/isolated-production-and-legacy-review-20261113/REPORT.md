## 实际缺陷：交付说明按路径错选音轨

复现步骤：同一生产单导入一份人工 MP3，分别为 3 个镜头保存不同文案，逐项确认并采用，再导出并生成交付包。3 条音轨的文件路径及 SHA 相同，音轨 ID 与文案不同。

已确认的工程和 `workspace.usedNarration` 保留了各镜头正确的音轨 ID、采用正文；交付 metadata 中第 2、3 镜头却都记录第 1 镜头的音轨和正文。对照 [最终单逐镜头结果](artifacts/delivery-text-check.json) 与 [两份独立新单复现](artifacts/delivery-metadata-reproduction.json)。这不是因为字幕使用独立模式，也不是新口播草稿覆盖了原音轨；被拒绝的新口播没有进入交付说明。

定位：`src/local-app/workspaceDeliveryCommands.ts` 组包时以 `episode_id + relative_path` 读取 `audio_tracks`，直接使用 `rows[0]`；没有同时按工程的 `sourceAssetId` 选中明确音轨。相对地，`readUsedWorkspaceNarrationVersions()` 已按明确音轨 ID 和内容哈希区分来源。对共享文件使用不同文案是可保存、可采用的受支持操作，技术交付检查没有覆盖此项跨文件语义一致性。

建议最小修复：统一调用权威音轨解析，核对生产单、明确音轨 ID、路径、SHA、采用指纹和实际使用窗口；旧工程没有 ID 时，仅在唯一匹配且来源可证实时回退，歧义应显式报告，不随便取首条，也不回退到可变草稿。给共享路径／不同轨、重新采用和原生保存补集成断言，并在组包前检查 metadata 与已确认工程的一致性。原历史包不能自动改写；修正时应建立新的明确版本。

私有快速复核命令已经执行，预期返回 1：

```sh
node /private/tmp/loop-production-audit-20261113-neuhw76_/check-delivery-source.mjs
```

输出：镜头 01 PASS，镜头 02 FAIL，镜头 03 FAIL。它比对真实生产导出的工程、实际使用记录和交付 metadata。原制作测试的绿色只代表其既有断言通过；本报告增加的业务对账仍然失败，缺陷尚未修复。

## 埋点完整性结论

已覆盖请求、任务、费用依据、主要候选和质量冻结，当前对账没有发现这部分重复计数或快照被覆盖。但不能把本轮称为「全部埋点完整、日常可以直接启用」。仍有以下边界：

1. **四步耗时不能直接得到。** 当前仅记录数据库 stage；准备、剪辑和本机导出都可能发生在 `script_approved`。应在权威业务完成点定义制作里程碑，再记录相应耗时；点击标签不等于推进生产。
2. **配乐／音效等素材使用不属于完整采用流水。** 本轮上传配乐确实进入工程，但没有增加 `candidate_adopted`。当前解析针对图片／视频候选及主口播，不能拿这 5 次算所有素材采用率。需要补明确的声音使用类型、准备项／素材身份与撤回规则。
3. **同步本机导出的耗时与资源可能漏记。** 该路径没有独立 Worker 导出任务；资源采样按 ready／running 任务判定活动，不能覆盖所有同步本机制作。宜单独登记导出开始／结束及活动范围，不能把 HTTP 等待伪装成 Worker 排队。
4. **交付完成事件目前证明技术验证完成。** 本轮 metadata 错选音轨仍会得到 `delivery_completed`。后续应增加业务内容一致性检查，并明确事件的验证版本；不能靠名字推定业务内容正确。
5. **未覆盖真实 Provider 和上线行为。** 没有视频 API、实际 GPT 图片模型、真实口播、供应商实付、视频远程查询下载，也没有切换日常包、开启日常采集或验证重启后的采样连续性。GPU 仍未知，统计 Dashboard 尚不存在。

这次已能在同一个隔离副本完成制作与埋点联验，不需要合并主分支。后续正式启用仍应针对最终代码／运行包验收，尤其补齐上述语义范围，再按 ADR-0057 操作。

## 旧流程与旧命名结论

本轮没有找到「只要换个名字就能把所有旧内容安全删除」的路径。实际新单仍产生旧审核包、旧镜头草稿和音轨记录，说明当前主链与历史兼容共用模型。

建议顺序：先修交付说明和历史关联恢复；再单独删除已核查的旧 `create_episode`；随后把当前制作基准／镜头／脚本合同从旧审核模型分离；把旧单接入当前工作区，明确停止哪些旧包执行；最后删除兼容入口、收敛 SQL 包装并统一名称。此前八类已逐项纳入 [方案](../../plans/production-workflow-replacement-20261113.md)，已清理的第 1 类不重复安排。

旧名字可以从当前接口和执行路径退出；历史冻结证据、归档 SQL 和备份中的名字继续作为版本资料保留。若还要求全部原运行包原样执行，它们依赖的签名就必须有兼容承接。不能以保留历史恢复为由永远保留所有旧业务，也不能以去掉旧名字为由删历史或放宽保护。
