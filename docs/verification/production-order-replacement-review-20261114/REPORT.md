## 实际发现

### 1. 正式输出含编辑网格

直接查看本轮成片抽帧，横图 contain 的上下留白含棋盘格。共享 SDK `src/editor/TimelineComposition.tsx:28` 定义 `GRID`，第 298 行用于非透明根背景。字节、编解码与交付 SHA 正确，不能证明画面背景正确。

建议在 SDK 渲染边界区分预览辅助网格和正式输出底色／透明策略。局部修复即可；不能通过裁满原素材或放宽导出检查掩盖问题。本轮未修改 SDK。

### 2. 原声浏览器用例等待了数据，却没有等命令完成

首次 33 项批次在 `productionSoundUse.integration.test.ts:133` 失败：准备项期望 1，读到 0。同源码独立诊断再次复现。按钮可用、双击成功；仅在私有测试副本增加失败现场取证，保留原失败，发现同一次 `prepareWorkspaceAudio` 随后返回 200，准备项确为 1，无重复请求。

该断言使用未配置超时的 `expect.poll`；现场安装的 Vitest 默认是 1000 ms。另一个私有验证副本只改为等待准确命令的回执，约 1678 ms 收到一次 HTTP 200，随后要求准备项恰好 1，再执行原有 Worker 提取、采用、桌面／390 px 窄屏、原生保存、声音事件及零旧草稿检查，全部通过。无产品改动、重试发请求、放宽数量或跳过保护。

因此证据支持测试完成条件不充分，未证实这条链的功能故障。建议后续修现有测试，使它等待具体命令完成再对账；本轮不写回。首次批次仍记录 32 通过、1 失败，不将私有专项绿色改称整轮通过。诊断的名称过滤跳过项不计通过。

### 3. 名称仍会误导，但并不都代表旧功能

本单人工音轨在任务表中仍叫 `generate_narration`，但没有外发、执行尝试或费用预留。当前埋点能区分真实请求，不能仅按任务名统计生成次数。原声页面也仍和「字幕与口播／口播关闭」等名称并存；应统一主声音的角色表达，而非据此断言无声。

当前图片、Pexels 和调用确认从旧计划 Store 导入 `productionHash`，其实际算法来自现有 `canonicalFingerprint`。先调整依赖且保持哈希结果不变，再退役 Store；无需新建哈希实现。
