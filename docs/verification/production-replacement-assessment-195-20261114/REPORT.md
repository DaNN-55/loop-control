## 两个导出专项发现

### 运行中的本机导出没有资源样本

使用真实一秒导出，在实际执行器入口暂停并保持为活动状态；占满业务连接池后，以单独的统计连接启动现有采样器。Owner 和运行时开关均开启，查询成功、无统计错误，但样本仍为 0。

原因是现有 `production_metrics_activity()`／采样器只判断 Worker 排队、运行和资源等待；同步本机导出没有 Worker 任务。当前正式运行时还把采样器接到业务池。单独连接只能解决连接等待，不能解决活动判断缺失。需同时增加本机活动来源与独立采样连接，保留原双开关、频率、未知 GPU 和原队列含义。[证据](evidence/local-export-resource-gap.json)。

### 导出开始事件导致两张独立单串行等待

同一 Owner 的两张独立生产单均由当前 HTTP 命令准备完成。第一张在渲染执行器入口暂停，随后提交第二张导出；第二张未进入渲染，实际 PostgreSQL 等待为 `Lock / transactionid`，查询为 `record_workspace_local_export`。释放第一张后，两张都成功生成真实 MP4。

195 在长渲染前写 `local_export_started`，内部 `append_production_metric` 同时更新 Owner／日期／事件类型／质量等分组的 `production_metric_daily` 行；行锁持续到业务事务结束。不同生产单的开始事件因此争用同一汇总行。建议在执行前只取得起始时间和登记进程内活动，完成后随业务结果原子持久化事件；跨开关覆盖期不能补造开始或准确时长。不是移除锁、放宽幂等或另造 Worker attempt。[证据](evidence/concurrent-export-observation.json)。

这项诊断通过表示已稳定复现问题，不表示问题已经修好。完整并发控制、开关切换、崩溃恢复和故障矩阵仍需在实施后验收。
