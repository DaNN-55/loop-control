## 结果

- 领域、Provider、原生帧取整与新 PostgreSQL/HTTP/文件集成合计 29 项通过；1 项按需浏览器夹具默认跳过。
- 新集成实际执行 14 项，覆盖 Owner/CSRF、只读查看、直接制作、幂等、并发、未知响应、真实回执写入失败、基准变化、单次审批、原稿恢复、逐镜音频/字幕、长镜头图片实际采用。
- `npm run check`、`npm run backend:build` 通过。
- 新模型结果来自受控本地 HTTP 服务，不是实际供应商推理；没有付费调用或素材生成，没有迁移日常数据库。

## 关键集成证据

1. 纯文本通过真实模型请求接口取得一份三镜头方案，审批前主脚本不变；篡改原文、时长、Owner 或提交客户端 plan JSON 被拒绝。采用后实际工程包含三个镜头，口播/字幕真实关闭。
2. 任意含 Markdown 标题及空行的原文无模型继续，保存后 GET 返回完整原文、一个逻辑镜头，不把内部 v3 当作原稿。
3. 15000 字原文、180 秒逻辑单镜头保存、启动、创建/重规划成功；随后真实导入 PNG，匹配 180 秒、注册 180 秒图片候选、准备并采用，原生图像 item 为 5400 帧且不再是占位。只放宽图片使用边界，视频 Provider 的生成参数未变。
4. 实际图片采用后再用三镜头模板重规划，口播保持关闭，字幕逐镜为 `[true,true,false]`。`subtitle:null` 且启用字幕时，实际字幕正文逐镜等于已审批口播；空口播/空字幕的启用方案在模型结果阶段拒绝，失败回执不能审批。
5. 普通非模板的显式字幕正文与关闭口播指令直接保存，实际字幕为独立模式，内容准确，口播保持关闭。
6. 有明确原稿时长和空目标时长时保留原稿总时长；其他原文将页面预计值作为有效总时长。修改请求必须引用同原文、同基准、同时长的完成方案。
7. 回执写入被真实数据库触发器故障中断后，再核对不会重发；网络断开后也不自动重发。基准在响应期间变化时返回冲突，但已完成模型回执保留。

## 修复中发现并重验的问题

- 新隔离 cluster 最初缺少 schema dump 不包含的 `loop_owner → loop_app` 角色继承；在隔离 cluster 补齐后，真实所有者流程通过，没有放宽生产权限。
- 独立 worktree 最初缺少 OpenChatCut 的 `tsx` 读取运行依赖；通过显式 `LOOP_TEST_OPENCHATCUT_ROOT` 只读引用已有工具运行时后通过，不修改日常运行配置。
- 180 秒测试最初单独运行依赖前序工作区；夹具改为按实际有无工程选择创建/重规划，随后准确复现图片 120 秒限制。两处图片使用校验同步 3600 后完整采用路径通过。
- 单纯空占位重规划未触发已有 native edit guard；加入“图片实际采用后重规划”才复现字幕关闭丢失。修复为 fresh project 明确绕过旧行的 native-edit guard，原工程打开与恢复仍保留保护；两种路径实际验证通过。
- 4.98 + 4.98 + 5.04 秒分别取整曾只有 449 帧；先失败的回归现验证为批准的 450 帧。

## 环境与边界

私有隔离 cluster 只监听独立 Unix socket，baseline 只有 schema 与迁移 ledger，没有日常业务数据。context 和夹具输出在 `.scratch/script-studio-20261117/`，不进入 Git。新建/修订及模型原文统一 20000 字符；既有大脚本仍可查看。逻辑时长 0.1–3600 秒不代表供应商单次生成上限。模型语义、实际供应商效果、UI 与真实导出不由这些受控模型测试证明。
