## 先区分已有实现与真正待做

当前源码已包含共享音频身份修复、历史主脚本投影顺序修复、186 旧建单 RPC 删除候选、v3 静态脚本合同，以及 187／188 独立制作基准与旧来源接入的部分实现。它们均不能当作日常已经更新。

187／188 已建立制作基准、稳定镜头和镜头版本；当前基准／镜头读取与本地镜头写入已经接到这些表，旧工程接入保留原始证据。实际使用前会读回物理文件，核对目录身份、SHA、大小和冻结 JSON；缺失／篡改／不可读会停止写入，不把 SQL 记录当成文件已验证。

但默认 `prepareAuthoredWorkspace` 仍生成 `storyboard/v1`，调用旧 `register_workspace_preparation`，新单仍会创建旧审核包；口播和字幕仍读取 `shot_preparation_drafts`，当前接口仍暴露旧包字段。仅有新表和回填不等于旧模型已经退出。

此前 188 阶段的 10 文件 42 项、类型检查和 schema 矩阵已通过，证据见[实施进度](../current-workflow-replacement-20261113/REPORT.md)。这些用例与本轮有重叠，不将次数相加。完整／逐项恢复、全部旧业务接入和最终 UI 仍须随最终模型验收。

## 最后可以清掉哪些旧内容

以下是达到条件后的目标清单，不是本轮删除批准，也不是声称当前已无依赖：

1. **旧手动命令组及专用 HTTP 入口**：`configureScriptProduction`、`pauseScriptProduction`、`applyScriptSettings`、`bindScriptVideo`、`renderScriptReview`、`prepareScriptPublish` 及 `/api/local/script-production`。先迁走必要能力并提供旧计划只读。
2. **七个拒绝 SQL 签名**：`queue_workspace_planning`、`replan_workspace_planning`、`save_planning_selection`、`plan_input_tasks`、`generate_input_shot_tts`、`apply_episode_configuration_repair_v2`、`apply_external_connection_repair`。先完成旧运行版本门槛，保持权限拒绝和未知请求证据。
3. **旧扫描与预检合同**：`script_production_scopes()`、`record_episode_worker_preflight()` 及其已退出的调用者。不能把空扫描重新变成自动发现，也不能用静默成功代替明确退役。
4. **旧审批初始化触发器与纯旧登记壳**：只有新单不再写旧模型、旧单接入完成、旧程序退出后才可删。租约、冻结输入、Owner 和文件校验职责必须留下。
5. **当前链中的旧字段／类型／别名和多代包装**：先迁走当前写入者、读取者、快照和恢复映射，再按实际职责收敛；不是见到 `legacy` 就删除。

`review_packages`、`shot_preparation_drafts`、`audio_tracks` 中的历史行、旧审批、冻结任务、原始 JSON、文件路径、SHA、已生效迁移和 ledger 不作为删除对象。旧业务停止使用后，可使旧存储成为历史只读来源；物理删历史表并不是本次「完全替换」的成功条件。

## 旧名字能不能全部换掉

当前界面、当前接口和执行代码可以统一新名称。历史备份、旧任务快照、原包和迁移里的名字应原样保留，由版本化适配器理解。既让旧二进制原样执行，又删掉它依赖的所有签名，两者不能同时保证。

建议候选：通用 `codexRunner` 改为媒体任务执行职责名；领取链按领取／租约职责合并命名；当前 `storyboard_package_id` 改用独立 `preparation_revision_id`。这些需要随真实调用迁移，不做全仓替换。`Episode`／`episodes` 是现行「生产单」实体名，若另想统一为 `production_orders`，应单列必要性与跨库／API／恢复成本，不因英文看着旧就顺带修改。

## 埋点联验结论与补齐方式

现有埋点可以与生产测试一起检查，本轮已联验；不需要另外部署日常服务。但全面覆盖仍有明确缺口：

| 缺口 | 建议补法 | 仍需保持 |
| --- | --- | --- |
| 四步制作耗时与返工 | 在主脚本确认、准备确认、工程保存／采用、精确导出／交付等权威成功点记录里程碑，关联基准／工程版本；定义返回前步和并行语义 | 点击页签不计业务完成；重复命令、重开不重复；停用期间不补造历史 |
| 配乐、音效、原声的完整使用 | 根据实际工程中可听素材及窗口记录使用／替换／撤回，明确声音类型和源身份；不只匹配候选或主口播的 ID 前缀 | 静音、裁切、删除与撤回有据；保留原素材；不把上传当成已经采用 |
| 同步本机导出的耗时和资源 | 使用独立可见的技术活动开始／结束记录，让其他连接上的采样器看到工作窗口；失败／中断也有状态 | 不能假造 Worker 排队；主机资源不冒充单任务用量；采集与资源双开关、默认关闭 |
| 交付完成事件的含义 | 标明实际验证合同和通过范围；技术文件通过与文案／来源一致性分别对账 | 已确认文件与 SHA、采用来源和实际窗口不放宽；供应商实付和 GPU 无证据仍为未知 |

现有只读汇总函数还不是 Dashboard。查询展示可以后续单独接入，不应为了展示先假设所有业务口径已经齐全。

## 推荐顺序与完成标准

1. **完成当前模型切换**：默认准备、候选、音轨、字幕、修订和任务回执统一；新单不新增旧审核包／旧草稿。187／188 是基础，不能作为终点。
2. **补当前语义**：v3 默认入口、显示名／草稿状态和三类统计缺口；随命令迁移一起验证，不从 UI 点击反推业务事实。
3. **接入旧作品并落实版本门槛**：真实旧计划、HTML、原生工程、原音轨／人工编辑以及在途／未知请求逐一对账。未知请求只核对或恢复，不自动重发。
4. **再删旧执行链**：满足前述条件后，删除旧手动命令、拒绝接口、扫描预检与无消费者触发壳；验证职责集中到当前边界和历史适配器。
5. **最后改名和生成基线**：当前 SQL／Worker／DTO 按职责统一，保留旧解码；新 clean 与前向升级、完整恢复和逐项恢复一致。

最终成功条件不是「搜不到旧单词」，而是新单不写旧业务结构、旧作品能由当前程序接入、旧程序被明确阻止执行、历史完整可恢复、所有现有保护等价。最终还需完整默认套件、实际宽窄 UI、新旧制作／恢复／故障矩阵和两轴审查；当前 17 项联验不能替代这些验收。
