# ADR-0033：逐次调用确认的客户端生命周期

状态：Accepted。日期：2026-11-10。依据本次状态机盘点与改进授权。

## 问题与决定

`useWorkspaceCallConfirmation` 原先分别保存 proposal、submitting、error、busy 和 pending promise。延迟回包回归复现了三种问题：准备中切换身份不会立即结束调用；旧确认成功会关闭新确认；旧确认失败会向新确认写入错误。仅比较身份字符串也无法区分 A → B → A 的两次进入。

保留现有 hook 接口，在原模块内使用有类型的状态联合：`idle → preparing → review → submitting → idle | failed`。`review | failed` 可取消回到 `idle`；`failed` 不允许重复确认。每次进入身份创建独立 owner，离开或卸载进入 `closed`，立即以 `AbortError` 结束等待中的调用。异步回复只有在 owner 和当前操作都匹配时才能推进状态。转换同步更新当前状态，再通知 React 渲染，防止同一渲染周期重复提交。

服务端事务、确认有效期、一次消费、执行快照、费用预留和供应商未知提交继续遵守 ADR-0024。离开页面不能撤回已经发出的服务端命令；客户端仅忽略离开后的回复，回到该生产单后由权威读取恢复任务状态。客户端确认事件也重新检查有效期，避免依赖按钮的上次渲染。

## 取舍

沿用 ADR-0030 的 owner 归属原则，不增加状态库或通用工作流解释器。数据库任务状态、供应商提交状态、产物发布状态和 UI 操作状态分别保留各自权威；它们表达不同事实，不能压成一个枚举。其他状态机在 [状态机清单](../architecture/state-machines.md) 登记来源、守卫与改动决定。

## 验证

通过 hook 与真实确认弹窗验证准备中切换、A → B → A、旧确认成功与失败、卸载、重复事件、失败后取消和到期后确认。保留金额、费用说明、参考图、命令参数及既有测试。使用受控延迟命令，不发出供应商请求。
